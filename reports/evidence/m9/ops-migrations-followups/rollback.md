# M9 / ops-migrations-followups — 되돌리기

착수 base **`6e6f953c`** · **복원 원천 `836e44ed`** · **실측 HEAD `2dbcc121`**(main 병합 커밋 — 이
브랜치에서 **복원 대상에 닿는 마지막 커밋**이고, 그 뒤는 evidence 뿐이다)

**원천이 base 에서 옮겨갔다.** 이 브랜치가 main(`836e44ed`, PR #144 머지분 — `c21adb2a`/PR #143 포함)을
병합했으므로 원천은 「이 브랜치가 **마지막으로 합친 main** 의 고정 SHA」다. 움직이는 `origin/main` 을
쓰지 않는다. 전제 둘을 **측정했다** — 그 SHA 가 HEAD 의 조상이고(`merge-base --is-ancestor` 참), 그
SHA 에 이 slice 의 **첫 산출물 커밋(`a5021d61`)이 없다**(같은 술어 거짓).

**원천이 옮겨도 복원되는 내용은 같다** — 복원 목록 여섯의 blob 이 `836e44ed` 와 착수 base 에서
**전부 동일**하다(파일별 `rev-parse <sha>:<경로>` 비교). 즉 그 사이 **남의 slice 가 내 in_scope 를
만지지 않았고**, 병합한 main 으로 복원하는 것이 누구의 줄도 떨어뜨리지 않는다. 이 확인이 없으면
원천 교체 자체가 「남의 변경을 base 로 되돌리는」 길이 된다.

이 절차는 **이 slice 가 main 에 없는 동안**을 전제한다(지금 성립 — 위 전제 ②). PR 이 머지된 뒤의
되돌림은 그 **머지 커밋 revert** 다 — 같은 복원은 머지 순간 아무것도 지우지 않으면서 exit 0 을 낸다.

## 1. 되돌리는 법

range revert 가 아니라 **in_scope 경로 한정 복원**이고 목록은 기계가 낸다.

```
MAIN=836e44ed                                                    # 마지막으로 합친 main 의 고정 SHA
EXCL=':(exclude)reports/evidence/m9/ops-migrations-followups'    # 자기 자신은 되돌릴 수 없다

changes() { git diff --name-status "$MAIN..HEAD" -- . "$EXCL"; }
mapfile -t RESTORE < <(changes | awk '$1=="M"||$1=="D"{print $2}')
mapfile -t DELETE  < <(changes | awk '$1=="A"{print $2}')

# M/D/A 밖의 상태(R·C 등)가 한 줄이라도 나오면 멈춘다 — 이 절차가 다루는 모양이 아니다.
changes | awk '$1!="M"&&$1!="D"&&$1!="A"' | command grep -q . && exit 3

git restore --source=$MAIN --staged --worktree -- "${RESTORE[@]}"
[ ${#DELETE[@]} -eq 0 ] || git rm -q -f -- "${DELETE[@]}"
```

**라운드마다 이 산출을 다시 돌린다** — 목록이 낡는 것이 이 결함의 실제 원인이다.

**hunk 격리가 필요 없다 — 병합 뒤에도 그렇다.** 이 절차가 hunk 격리를 요구하는 상황은 「복원 대상에
남의 slice 줄이 섞여 있다」인데, 위 머리말이 그것을 **측정으로 배제했다**: 원천의 그 여섯 파일이
착수 base 와 blob 동일이므로 원천 복원은 **이 slice 의 줄만** 걷는다. 공유 파일
(`docs/runbook/**` · `tools/db-rehearsal.sh` · `AppHttpDependencyGateTest.kt`)도 그래서 **원천 복원
한 번**으로 끝난다.

**병합 커밋의 충돌 해소 줄도 없다** — 그쪽이 hunk 격리를 깨는 전형인데(어느 커밋 해시로도 걷히지
않는다), 이 병합은 **충돌 0**(`merge-tree` 충돌 표지 0 · unmerged 0)이고 내 여섯 파일의 blob 이 병합
전후로 동일하다. 즉 병합이 복원 대상에 손으로 해소한 줄을 남기지 않았다.

**`DELETE` 는 비어 있을 수 있다** — 이 slice 가 만든 새 파일은 evidence 뿐이고 그것은 `EXCL` 로
빠진다. 그래서 `git rm` 을 조건부로 둔다(빈 pathspec 은 exit 128 이다).

## 3. 실측 (버릴 clone, `git clone --no-hardlinks`, detached)

| 단계 | 실측 |
| --- | --- |
| ① 목록 산출 | 원천 대비 **복원 6**(전부 `M`) · **삭제 0** · **M/D/A 밖의 상태 0 줄** |
| ①′ 목록 완전성 | 원천과 다른 경로 전부가 목록 안에 있다 — `comm -23` **0 줄** |
| ② 명령 exit | `git restore --source=$MAIN --staged --worktree --` **exit 0**(`git rm` 갈래는 목록이 비어 돌지 않았다 — 그 조건부가 빈 pathspec 의 exit 128 을 막는다) |
| ③ 복원 뒤 `git diff $MAIN -- <복원 경로>` | **0 줄** |
| ③′ **내 표지 0 · 남의 표지 보존** | 표지 **열둘**(파일 여섯 × 각 축 하나)이 전부 기대값 — 내 표지 여섯 모두 **0**, 남의 표지 여섯 모두 **원천 값과 같다**. 어긋난 줄 0. 기대값은 문서에 박지 않고 **원천에서 그때 다시 센다**(`git show <원천>:<파일>`) |
| ④⑤⑥ | **`./gradlew --no-daemon check` exit 0** · 37m23s — 433 task 중 **278 실행 · 155 cache**. 전건이므로 compile·test·게이트 셋을 한 번에 든다. 되돌린 트리에서 게이트가 초록이라 보완 경로가 필요 없었다 |

**이번 ④⑤ 는 갈음이 아니라 실행이다.** 병합이 들여온 main 변경이 두 모듈의 test 입력을 바꿨으므로
cache 가 재생할 입력이 없었고, task 상태 줄에 **`:adapters:test`·`:app:test` 가 표식 없이** 떠 있다
(`FROM-CACHE`·`UP-TO-DATE` 가 아니다). 앞 라운드처럼 「트리 동일성으로 갈음」하는 설명이 이번에는
필요하지 않다. cache 에서 온 것은 이 slice 가 만지지 않는 모듈 둘(`shared-kernel`·`workflow`)이다.
⑥ 의 게이트 층도 실행 목록에 있다 — 누출 스캔 · 모듈별 게이트 test 실행/등재 · 크기 게이트.

실행 여부를 **task 상태 줄**로 세는 이유는 결과 XML 의 mtime 이 증거가 아니기 때문이다 — cache 적중도
출력을 풀어 써서 mtime 을 새것으로 만든다.

**③′ 의 표지는 어휘 grep 이 아니라 항목 집합이다.** 파일마다 축 둘을 고르고(이 slice 가 들여온 식별자
하나 · 남의 slice 가 이미 쓰던 식별자 하나) **원천 값과 HEAD 값을 미리 양쪽에서 재** 두고, 복원 뒤의
값이 원천 값과 같은지 본다 — 「0 이 나왔다」만 보면 파일이 통째로 비어도 통과하므로 남의 표지 쪽을
함께 센다. 남의 표지 둘은 이 slice 가 사용 횟수를 바꿨고(하나는 +1, 하나는 −1 — 상수로 모았다),
그래서 **원천 값으로 돌아왔는지**가 구별력 있는 수가 된다.

**⑥ 을 전건으로 든 이유**: 이 slice 가 닿은 게이트가 한 종류가 아니다(ktlint·detekt·size·게이트 test
실행/등재·누출 스캔). 그 집합을 손으로 열거하면 빠뜨린 것이 곧 안 돌린 게이트가 되므로 job 단위로
들었다.

## 4. 실측이 유효한가 — verifier 가 보는 술어

evidence 커밋은 언제나 실측 뒤에 오므로 「실측 HEAD == 판정 SHA」가 아니다. 대조할 것은 **그 사이에
되돌림 대상이 움직였는가**다:

```
git diff --name-only <실측 HEAD>..<판정 SHA> -- <§1 의 RESTORE 목록 경로들>
```

빈 출력이면 유효하고 한 줄이라도 나오면 미검증이다(대조 경로는 이 문서 §1 의 목록 자신이다 —
되돌리지 않는 팀장 레인 문서의 편집이 멀쩡한 실측을 미검증으로 만들지 않게 한다).

| 술어 | 결과 |
| --- | --- |
| §4 대조(실측 HEAD `2dbcc121` 기준, 이 문서를 쓰는 시점) | **0 줄** — 되돌림 대상이 움직이지 않았다 |

이 뒤에 붙는 커밋은 **evidence 뿐**이고 그 경로는 §1 의 `EXCL` 로 복원 대상 밖이다 — 그래서 판정
SHA 가 evidence 커밋이어도 이 술어는 0 줄로 남는다. 한 줄이라도 나오면 그것은 산출물이 다시 움직인
것이므로 ①~⑥ 을 그 HEAD 에서 다시 돌려야 한다.

**실측 HEAD 를 병합 커밋으로 고른 이유.** 이 slice 의 마지막 **in_scope** 산출물 커밋은 `57a1a22f`
지만, 되돌림은 **지금의 트리**에 적용되고 그 트리에는 병합이 들여온 main 변경이 들어 있다. 그래서
병합 커밋에서 재야 ④⑤⑥ 이 실제로 되돌릴 트리를 잰다(`57a1a22f` 에서 재면 main 변경이 없는 트리를
재는 것이고, 그 결과는 판정 대상에 대해 아무 말을 하지 않는다). 병합 커밋은 복원 **목록**을 바꾸지
않았다(위 ①) — 바꾼 것은 그 밖의 파일들이고, 그래서 이 술어가 0 줄이다.

**직전 라운드의 실측(`83d97128`, 원천 `6e6f953c`)은 옮기지 않았다.** 남은 LOW 둘이 복원 목록 안의
파일 둘을 다시 만져 그 실측이 낡았고, 그 사실을 이 자리에 선언해 두었다가 **병합 뒤 원천·목록·①~⑥
을 전부 다시 내서** 교체했다. 낡은 수를 그대로 둔 채 통과로 적지 않는 것이 이 절의 규율이다.
