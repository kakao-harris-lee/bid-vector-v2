# M9/paper-bid 설계 검토 (구현 전)

## 0. 위협 모델 경계

운영자가 **서면(페이퍼) 연습의 소식과 실제 투찰의 소식을 같은 알림함에서 섞어 받지 않는다** —
한쪽이 다른 쪽의 항목을 덮어쓰지 않고, 읽음·계수·묶음이 두 축을 합치지 않으며, 어느 항목이
어느 축인지가 화면과 저장 층 양쪽에서 **값으로** 선다.

경계 **밖**: 발송 채널, 페이퍼 건의 **판정 규칙**(어떤 전이가 가능한가 — 7B 의 일), 공고 원천
판정, 계정 안읽음 배지를 축별로 가르는 UX 결정(등재만 한다).

## 1. 열거인가 구성인가

- **구성**: 투찰 종류 축은 **키**에 산다(`NotificationInboxRecord`·`NotificationItemKey`·PK),
  사실(`NotificationFact`)에 싣지 않는다. 같은 「마감 D-1」은 두 연습에서 **같은 사실**이고
  갈리는 것은 「어디에 적히는가」다 — record 는 이미 키 축 둘(계정·공고)을 들고 fact 는 사건만
  든다. 사실에 실으면 네 `data object` 가 `data class` 가 되고 같은 사건이 두 값으로 갈린다.
- **구성**: 「이 종류가 투찰 종류 축을 갖는가」는 `NotificationKind` 전수 `when`
  (`bidKindAxis`)이고, 그 표 하나에서 ⓐ 기록 경로의 `require` ⓑ 저장 층 짝 CHECK 의 기대
  파티션 ⓒ test 모집단이 **함께** 나온다. 종류를 더하면 답을 주지 않고는 컴파일되지 않는다.
- **구성**: `BidKind`(bidding) → `NotificationBidKind`(알림함) 사상이 전역 `when` 하나이고,
  **두 어휘의 1:1 등식**을 test 가 잠근다 — bidding 에 종류가 하나 더 생기면 이 등식이 붉어
  「조용히 REAL 로 접기」가 성립하지 않는다.
- **열거**: 투찰 종류 어휘 셋과 짝 CHECK 는 DDL 이라 열거다. 그 열거가 Kotlin·openapi·화면과
  같은 집합이라는 **등식**이 세 자리에서 돈다(DB CHECK ↔ enum, openapi ↔ enum, 생성 타입 ↔
  손 코드 표).

### 왜 `bidding.BidKind` 를 알림함이 직접 들지 않는가

V24 가 `bidding.BidOutcome`(값이 같았다)을 재활용하지 않은 것과 **같은 축**이다. 알림함의 키
어휘는 저장 층 CHECK 와 집합 등식을 이루는 `notificationinbox` 패키지의 닫힌 어휘이고, 그것을
`bidding` 의 enum 에 묶으면 알림함이 입찰 모듈 없이는 서지 않는다(7C③ 이 이 패키지의 의존을
`procurement.NoticeId`·`workflow.access.AccountId` 둘로 묶어 둔 사유). 그리고 **두 집합은
실제로 다르다** — 알림함 쪽에는 「건에서 오지 않은 알림」의 자리가 하나 더 있다(아래).

### 축이 부분적이라는 사실 — `NONE` 의 근거

알림 원천이 **셋**이고 그 중 하나는 건이 아니다.

| 원천 | 종류 | 투찰 종류 축 |
| --- | --- | --- |
| 되비춤(`BidCaseWorkflow`) | 개찰 완료 · 낙찰 확정 | 건의 종류 |
| 훑기(`SweepNotifications`) | 마감 D-1 · D-0 · 서류 D-2 · 공고 변경 | 건의 종류 |
| 투찰가 요청(`BidPriceRequestFactory`) | 투찰가 요청 기록 | **없다** — 공고에 붙는다 |
| (원천 미구현) | 새 후보 | **없다** — 건이 생기기 **전**의 소식이다 |

PK 열은 NOT NULL 이므로 NULL 로 「없음」을 적을 수 없다. 그래서 어휘에 `NONE` 을 두고, 그 값이
**어느 종류에만 올 수 있는지**를 짝 CHECK 가 못박는다 — 「투찰가 요청을 REAL 로 적어 두기」와
「마감 알림을 NONE 으로 적어 두기」가 둘 다 DB 에서 거부된다.

## 2. 새 public 표면 전수 (값 획득 축)

| 표면 | 값이 들어오는 자리 | 무엇이 막는가 |
| --- | --- | --- |
| `NotificationBidKind`(셋) | 어댑터 codec(`valueOf`) · DB 행 · 사상 함수 | 어휘 등식 셋(DB·openapi·화면) + `BidKind` 1:1 등식 |
| `NotificationKind.bidKindAxis` + `BidKindAxis` | 기록 경로의 `require` · 짝 CHECK 기대 파티션 | 파티션 고정 등식(축별 집합) + 실 DB 전수 교차 |
| `NotificationInboxRecord.bidKind` | 원천 **셋** 전부 | 소진 사상(되비춤·훑기) · 명시 `NONE`(투찰가 요청) · `init` 짝 검사 · 짝 CHECK |
| `NotificationItemKey.bidKind` · 묶음 키 | HTTP 본문 두 자리 | 허용 키 등식 + 어휘 전수 판독(`valueOf` 아님) + 계약 test |
| V25 의 열·제약 둘·PK | 모든 INSERT·UPDATE | 제약 수 래칫(7) · 열 래칫 · pkey 열 목록 래칫 · 어휘 등식 · 교차 |
| V25 의 INSERT GRANT | 앱 역할의 모든 INSERT | 권한 test(출하 상수 직접 실행 + 음성 대조) |
| `UPSERT_ITEM`·`MARK_NOTICE_READ` 의 새 bind(internal) | `Jdbc*` 둘 | 호출자 둘뿐 · 출하 상수 직접 실행 test · 실 DB 거동 |
| openapi `bidKind`(항목 + 요청 둘) · 생성 타입 · 화면 표 | wire | `satisfies Record<…>` · 바이트 등식 · 계약 test |

**「경계로 처리」 행 없음** — 위 여덟은 모두 실측 대상이다.

## 3. 우회 (≥5)

1. **열만 더하고 PK 는 그대로** — 행은 여전히 덮어쓰이고 열은 「마지막에 쓴 쪽」이 된다.
   화면은 종류를 보여 주므로 **거짓말이 더 나빠진다**. 막는 것: pkey 열 목록 래칫 +
   「같은 공고 PAPER+REAL → 항목 2」 실 DB test + 그 둘이 서로의 detail·읽음을 바꾸지 않는
   음성 대조.
2. **PK 는 바꾸고 `ON CONFLICT` 키는 그대로** — upsert 가 네 열로 충돌을 보면 PostgreSQL 이
   「유일 제약이 없다」로 **거부**한다. 막는 것: **거동 하나가 두 꼴을 함께 닫는다** — 출하
   상수를 그대로 쏘아 ⓐ 같은 다섯 열 키의 재기록이 **1 행**(멱등)이고 ⓑ 투찰 종류만 다른
   재기록이 **2 행**임을 잰다. 축이 `ON CONFLICT` 에서 빠지면 ⓑ 가 갱신으로 떨어져 1 행이고,
   PK 와 다른 열 집합을 적으면 문장 자체가 거부된다. 문자열을 파싱하지 않는다.
3. **가드를 하나만 걷는다**(되비춤만, 또는 훑기만) — 페이퍼가 결과 알림은 받고 마감 알림은
   못 받거나 그 반대가 된다. 막는 것: 원천 **둘 각각**의 실 DB·순수 test(페이퍼 건이 후보에
   들어온다 · 페이퍼 전이가 항목을 남긴다) + 훑기 질의에 투찰 종류 리터럴이 없음을 **거동**으로
   재는 자리(후보 집합이 두 종류를 모두 담는다).
4. **backfill 을 한 값으로 접는다**(기존 행 전부 `REAL`) — 투찰가 요청 항목이 **실투찰로
   라벨된다**. 그 행은 짝 CHECK 밖이라 `ADD CONSTRAINT` 가 **검증에서 실패한다**(순서상 잡힌다).
   막는 것: 짝 CHECK 를 backfill **뒤**에 세우는 순서 + 두 종류의 기존 행이 `'NONE'` 으로 가는
   것을 적용 리허설에서 계수로 확인.
5. **열에 기본값을 남긴다**(`DEFAULT 'REAL'`) — bid_kind 를 빠뜨린 INSERT 가 **조용히 실투찰로**
   들어간다(코드가 아니라 DDL 이 값을 지어낸다). 막는 것: backfill 뒤 `DROP DEFAULT` + 열 래칫의
   「기본값 있음」 축(`created_at` 만 true) + 열을 빠뜨린 INSERT 가 **거부되는** 양성 대조.
6. **짝 CHECK 를 느슨하게 둔다**(어휘만 닫고 짝은 안 짓는다) — 마감 알림이 `NONE` 으로,
   투찰가 요청이 `PAPER` 로 들어간다. 막는 것: 종류 전수 × 투찰 종류 전수 **교차**(실 DB), 기대
   집합은 `bidKindAxis` 표에서 **짓는다**(손으로 적으면 둘째 정본이 된다). 어휘 등식만으로는
   **보이지 않는 자리**다(V24 변이 ③b 가 같은 축을 실측했다).
7. **투찰 종류를 UPDATE 권한에 넣는다** — 앱이 항목을 다른 축으로 **옮겨** 중복 억제를
   우회하고(한 사실이 두 항목이 된다) 페이퍼를 실투찰로 바꿔 쓸 수 있다. 막는 것: 열 단위
   GRANT 에서 UPDATE 목록 **밖**이고, 앱 역할로 직접 쏘는 권한 test 가 그 UPDATE 의 실패와
   네 열의 성공(음성 대조)을 같이 잰다.
8. **목록 질의의 파티션·정렬에 축을 빠뜨린다** — 묶음 계수가 두 축을 **합쳐** 세고(「안읽음 2」가
   실은 페이퍼 1 + 실투찰 1), 정렬에 없으면 두 축의 항목이 섞여 화면의 연속 접기가 한 묶음을
   여럿으로 쪼갠다. 막는 것: 묶음 계수 test(같은 공고 두 축 → 각 묶음 `itemCount` 1) + 목록
   순서 test(두 축이 **연속**한다) + 화면의 묶음 키 등식.
8b. **묶음 읽음 처리에 축을 빠뜨린다** — 「묶음 전체 읽음」이 **남의 묶음까지** 읽는다(페이퍼를
   읽으면 실투찰 소식이 사라진다 — 이 slice 가 막으려는 바로 그 일의 읽음 축 판본). 막는 것:
   실 DB test(한 축만 읽히고 다른 축은 안읽음으로 남는다) + 허용 키 등식(본문에 축 칸이 있다).
9. **화면이 두 축을 같은 얼굴로 그린다** — 행은 둘인데 운영자가 어느 것이 연습인지 모른다.
   막는 것: 묶음 머리의 축 라벨 표 + `satisfies Record<NotificationBidKind, …>` + testId 에 축이
   들어가 두 묶음 locator 가 갈린다.
10. **생성 타입을 손으로 고친다**(또는 openapi 만 고치고 재생성을 잊는다) — 막는 것: 바이트 등식
   (`api:types:check`).

## 4. 과잉·미달

- **과잉 아님**: 축을 `Boolean isPaper` 로 두는 길은 「건에서 오지 않은 알림」을 표현하지 못하고
  (그 자리에 `false` 를 적으면 실투찰과 같은 값이 된다) DB 어휘 등식도 서지 않는다. 셋이므로
  열거가 맞다.
- **과잉 아님**: `BidKindAxis`(둘)를 `Boolean` 대신 둔 것은 `ReadResetPolicy` 선례와 같은 자리다 —
  파티션 등식이 이름으로 서고, 축이 늘면 사상 자리에서 컴파일이 막힌다.
- **미달 자리 하나**: 계정 **안읽음 배지는 한 수**다(`X-Unread-Count`). 페이퍼 안읽음이 그 수에
  섞여 들어가므로 「실투찰만 N건」을 배지로는 알 수 없다. 헤더를 둘로 가르는 것은 UX 결정이라
  하지 않고, 대신 ⓐ 그 수가 두 축을 **모두 센다**는 것을 test 로 못박고 ⓑ 묶음 계수는 축별로
  갈라 화면에서 구분이 선다. 알려진 제한에 등재한다.
- **미달 자리 둘**: 페이퍼 건의 **알림 내용**은 실투찰과 같다(문면이 축 라벨로만 갈린다).
  「연습이라 마감이 실제 마감이 아니다」 같은 축별 문면 차이는 이 slice 가 세우지 않는다.

## 5. PK 교체 절차 · backfill · 인덱스 · GRANT

**순서가 정확성의 일부다** — 다음 순서 말고는 성립하지 않는다.

1. `ADD COLUMN bid_kind TEXT NOT NULL DEFAULT 'REAL'` — 기본값이 있어야 기존 행이 NOT NULL 을
   만족한다(PG 11+ 는 메타데이터 연산이라 표를 다시 쓰지 않는다).
2. **backfill 두 UPDATE** — 건에서 오지 않는 종류 둘을 `'NONE'` 으로. 나머지는 1 의 기본값이
   이미 `'REAL'` 이고 그 값은 **추측이 아니라 사실**이다(원천 둘이 가드로 실투찰만 적었다).
3. `ALTER COLUMN bid_kind DROP DEFAULT` — 2 뒤에 반드시. 남기면 우회 ⑤ 가 열린다.
4. 어휘 CHECK + 짝 CHECK **추가**(backfill 뒤라 기존 행 검증을 지난다 — 2 보다 앞서면 실패한다).
5. `DROP CONSTRAINT notification_inbox_pkey` → `ADD PRIMARY KEY (…)`. `IF EXISTS` 를 **붙이지
   않는다**(이름 추측이 틀렸으면 그 자리에서 실패해야 한다 — V24 가 같은 판단을 했다).
6. `GRANT INSERT (…)` **전 목록 재선언**(새 열 포함). UPDATE 목록은 **그대로** — 투찰 종류는
   앱이 바꿀 수 없다(우회 ⑦).

**인덱스 둘 — 더하지 않는다**(재검토 결과).
- `(account_id, occurred_at DESC)` 는 목록의 계정 경계·정렬 축이고 새 열과 무관하다.
- `(created_at)` 는 보존 cutoff 축이고 무관하다.
- 새 PK 열 순서를 `(account_id, notice_number, notice_round, bid_kind, kind)` 로 두면 묶음 읽음
  처리의 술어가 그 **접두**가 된다(앞 판 PK 에서는 `account_id` 만 접두였다). 즉 축이 늘면서
  질의 하나가 **나아진다** — 그래서 보조 인덱스를 더할 근거가 없다. 더하면 쓰기 비용과 스냅샷
  래칫만 늘고 읽는 질의가 없다.

## 6. V25 되돌림 두 갈래

- **미적용 DB**(머지 전 로컬·CI): V25 파일 삭제 + in_scope 경로 `git restore`. Flyway 이력에
  없으므로 흔적 0.
- **적용 DB**: forward-fix 새 V 하나. 순서가 2 와 **거꾸로**다 — ① 페이퍼 행을 **처분**하고
  ② 제약 둘을 지우고 ③ PK 를 V23 의 네 열로 되돌리고 ④ 열을 떨어뜨린다. 페이퍼 행 처분이
  선택이 아니라 **순서상 필수**다: 남기면 옛 PK 복원이 중복 키로 실패한다(같은 공고의 PAPER·REAL
  두 행이 네 열에서는 같은 키다). 처분은 **삭제**이고 **소유자 연결**의 일이다(앱 역할에 DELETE
  권한이 없다). `'NONE'` 행은 반대로 **남긴다** — 열이 사라지면 그 축도 사라지고 항목 자체는
  옛 코드가 읽을 수 있다. 절차와 실측은 `rollback.md`.
- **두 갈래는 배타다**: 적용 뒤에 V25 파일을 지우면 Flyway `validateOnMigrate` 가
  「applied migration not resolved locally」로 **기동을 막는다**(V24 선례).
