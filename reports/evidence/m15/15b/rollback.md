# M15 / 15B — rollback

되돌림은 **range revert 가 아니라 in_scope 경로 한정 복원**이다. 목록은 손으로 적지 않고
`git diff --name-status <복원 원천>..<실측 HEAD>` 가 기계로 낸다 — 라운드마다 재산출한다.

```
착수 base: 99f2fb25989078d7ab1640de0dc8e399f5d1688d
복원 원천: d2c0513db4bd9abf5b2a9cae0c17e1e174fc470d   # 15A(PR #191)가 들어온 main — 이 브랜치가 병합했다
실측 HEAD: 8035759db439442c0c1fe5335580b32d6a387127   # 수정 라운드 3 의 마지막 산출물 커밋
```

## 복원 명령

`<M>` 은 그 range 의 `--diff-filter=M` 경로 전수(52), `<A>` 는 `--diff-filter=A` 경로 전수(19)다.
`--diff-filter=D` 는 **0** 이다(이 slice 는 파일을 지우지 않는다). 셋 다 명령으로 뽑고, 개별
인자로 넘긴다(`-A`·`.` 를 쓰지 않는다).

```
git diff --name-only --diff-filter=M <원천>..<HEAD>          # <M>
git diff --name-only --diff-filter=A <원천>..<HEAD>          # <A>
git restore --source=<원천> --staged --worktree -- <M>
git rm -f -- <A>
```

`<A>` 를 `git restore` 로 되돌릴 수 없는 이유: 그 경로들은 원천에 **없다**(pathspec 이 맞지
않는다). 신설 파일의 되돌림은 삭제다.

## 복원 원천을 바꿨다 (수정 라운드 3)

라운드 2 까지 원천은 착수 base 였다. 이 브랜치가 **15A 가 든 main(`d2c0513d`)을 병합**했으므로
원천은 그 커밋이다 — 착수 base 로 복원하면 15A 의 변경(계정별 전략·프로필, `AccountId` 패키지
이동, V28)까지 함께 지워진다. 그 SHA 에 이 slice 의 변경은 없다(첫 산출물 커밋이 그 뒤에 선다).

**셋째 단언**(원천을 바꾸면 재는 것): 복원 대상 blob 이 착수 base 와 새 원천에서 **같지 않다** —
15A 가 공유 파일과 접근 경로를 함께 바꿨다. 그래서 계수를 새 원천 기준으로 **다시 셌다**
(`M` 42 → 52, `A` 19 그대로). 아래 실측은 전부 새 원천으로 돌린 것이다.

**머지 뒤의 되돌림은 PR revert 가 받는다**(병합 커밋의 충돌 해소 줄은 경로 한정 복원 밖이다).

## 실측 (임시 clone, 2026-11-22 · 수정 라운드 3 에서 재산출)

버릴 clone 을 `8035759d` 에 두고 위 네 명령을 그대로 돌렸다.

| 축 | 값 |
| --- | --- |
| ① 명령 종료 코드 | `git restore` 0 · `git rm` 0 |
| ② D/M 계수 | 삭제 19 · 수정 52 — 산출 목록의 `A` 19 · `M` 52 와 같다. `--diff-filter=D` 는 0 |
| ③ 남은 diff | `git diff <원천> --name-only` **빈 출력** |
| ④~⑥ 갈음 | **트리 동일성** — `git diff-index --quiet <원천>`(워크트리)와 `--cached <원천>`(색인)이 **둘 다 exit 0**. 되돌린 트리가 원천과 바이트까지 같으므로 컴파일·test·게이트를 다시 돌리지 않는다 |
| 미추적 | **없다**(`git status --porcelain` 의 `??` 0) |

## 실측 HEAD 이후의 이동

실측 뒤에 선 커밋은 **evidence 뿐**이다. 그 커밋이 움직인 경로는 전부 **복원 원천에 없는
신설 파일**(`reports/evidence/m15/15b/` 아래)이라 복원 명령에서 `git rm` 쪽에 든다 — 그 넷은
실측 HEAD 에 **이미 있었으므로** `A` 계수는 그대로이고(늘지 않는다), 움직인 것은 그 파일들의
**내용**이다(r3 verifier L-4 의 문면 정정). 열거와 「원천 부재」 확인은 검증 레인이 한다.

실측 HEAD 와 판정 SHA 사이에 **병합 커밋이 없다**는 것도 같은 자리에서 본다
(`git rev-list --merges <실측 HEAD>..<판정 SHA>` 가 빈 출력) — main 병합이 뒤에 오면 실측
자리가 그 병합 커밋으로 옮겨가야 한다.

## 복원 뒤 사라지는 것 / 남는 것

- 사라진다: `POST /api/accounts` 와 그 화면·여정, V29(열 단위 INSERT·DEFAULT 셋·잠금 상한),
  `SignUpPolicyData`·`SignUpThrottle`·`AccountSignUpPort`, `OPEN_ROUTES` 의 둘째 자리,
  그리고 **평가 커밋의 run 당 계정 상한 둘**(설정 키가 사라지고 러너가 다시 청중 전원을 돈다 —
  그 run 은 계정 수에 선형인 비용으로 돌아간다, `OPEN-M15-EVAL-COST-PER-ACCOUNT` 재개봉).
- 남는다: 로그인·세션 경로 전부(이 slice 는 그 자리를 **더하기만** 했다), 운영자 명령 `rotate`,
  15A·15C 의 표(건드리지 않았다), 15A 의 계정별 분리 전부(복원 원천이 그 커밋이다).
- **이미 만들어진 계정 행은 DB 에 남는다.** 복원은 소스만 되돌리고 데이터를 지우지 않는다 —
  그 계정들은 로그인으로 계속 들어온다(권한이 새는 방향이 아니다). 행을 지워야 하면 소유자
  연결의 일이고 이 slice 밖이다.

## 이미 반입된 DB 가 있을 때 (verifier r1 LOW-3)

위 복원은 **소스만** 되돌린다. V29 가 이미 적용된 DB 에 V29 없는 판을 띄우면 Flyway 의 기본
검증이 「적용된 마이그레이션이 소스에 없다」로 **기동을 거부한다**. 그래서 반입 뒤의 되돌림은
경로 한정 복원이 아니라 **전방 마이그레이션**이다:

```
REVOKE INSERT (login_name, passphrase_hash) ON account FROM bidvector_app;
-- DEFAULT 셋은 되돌리지 않는다. 그 값은 앱이 고를 수 없는 자리이고(INSERT 권한 밖),
-- 운영자 명령은 명시 값을 실으므로 거동이 그대로다.
```

그 커밋은 소스 쪽에서도 가입 경로를 함께 닫는다(아래 「비활성화 경로」) — 권한만 걷으면 가입이
500 이 아니라 권한 거부로 떨어지고, 그 사실이 화면에 「가입하지 못했습니다」로만 보인다.

## 비활성화 경로(되돌리지 않고 막기)

소스를 되돌리지 않고 가입만 닫으려면 **`OPEN_ROUTES` 에서 그 한 줄을 빼면 된다** — 그 순간 기본
거부 필터가 `POST /api/accounts` 를 401 로 돌려보내고, 집합 등식 test 둘이 그 변경을 드러낸다.
DB 권한까지 닫으려면 `REVOKE INSERT (login_name, passphrase_hash) ON account FROM bidvector_app`
한 줄이 다음 마이그레이션에 선다(V29 의 역이고, 그 뒤 가입은 500 이 아니라 **권한 거부**다).
