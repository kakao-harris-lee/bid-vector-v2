## 2026-08-26 — 「먼저 답할 것」 8건 중 4건 확정

### OPEN-ML-01 · ML 수학 커널 8개의 언어 경계 — **결정: (a)**

- **결정**: 8개 커널 전부 Python `ml-engine`으로 보낸다. 경계 규칙은
  "수학 커널 = ml-engine / 업무 판정 = Kotlin".
- **선행 질문에 대한 운영자 답**: `app/domain/settlement_maturity.py`(133줄)를
  **ML 커널로 본다**(2026-08-26).
- **따라서 확정되는 경계**: 성숙도 **계산**(곡선·임계 산출)은 ml-engine이 소유하고,
  성숙도 값을 받아 내리는 **업무 판정**(embargo 적용 여부, 게이트 통과 여부)은
  Kotlin이 소유한다. SET-06은 후자만 소유한다.
- **근거**: 8개 전부 순수·stdlib 전용(ML-11.1). 분리 시 학습·추론이 같은 피처 모듈을
  import하는 training-serving skew 방지 구조가 깨진다
  (`app/ai/predictors/award_rate_gbm.py:60-66` ↔ `app/services/ml_training/award_rate_gbm.py:52-59`).
  `scipy`·`sklearn` import 0건이며 KDE는 손수 구현한 반사 보정 KDE라 라이브러리 대체 불가.
- **하류**: ADR 0001(목표 아키텍처)이 이 경계를 기록한다. M5 이식 대상 목록이 8개로 확정된다.
- **잔여**: SET-06 acceptance가 "성숙도 계산"과 "성숙도 기반 판정"을 분리해 서술하는지
  0C에서 확인이 필요하다.

### OPEN-OPS-05 · 브로커 선택 — **결정: (a) 브로커 없음**

- **결정**: 메시지 브로커(RabbitMQ 등)를 V2에 두지 않는다. 스케줄·outbox·재시도는
  DB 기반으로 구현한다. 측정된 필요가 나타나기 전에는 브로커를 도입하지 않는다.
- **운영자 답 원문 취지**(2026-08-26): "RabbitMQ로 얻는 이득이 없을 것 같고 불필요한
  인프라. gRPC로 Python ML과 Kotlin service layer가 연결되고, 요청에 대한 부분은
  callback 등으로 처리해 통보하는 형식이면 충분. 적은 개발 비용 선택."
- **선행 질문 1(기존 인프라 재사용 제약)**: 제약 없음 — 재사용하지 않는다.
- **선행 질문 2(운영 형태)**: **1인 운영**이며 팀이 아니다(2026-08-26).
- **근거**: `v2-지침서.md` §7("측정된 필요 없이 Spring Statemachine, WebFlux, Kafka 같은
  무거운 도구를 추가하지 않는다"). legacy outbox의 가치는 코드가 아니라 at-most-once
  모호성 격리 **정책**에 있고 어떤 기반 위에도 얹힌다(OPS-21). 1인 운영이므로 실시간
  경보 요구가 낮아 브로커의 관측 요구가 정당화되지 않는다.
- **범위 주의(기록 필수)**: 운영자 답의 gRPC·callback은 **Kotlin ↔ Python ML 호출 경로**를
  가리킨다. 이 결정이 닫는 것은 그와 별개인 **내부 workflow 큐**(주기 수집, 알림 발송,
  재시도, outbox)의 기반 선택이다. 두 축을 같은 결정으로 접지 않는다.
  ML 호출 경로의 전송은 ADR 0003(gRPC/Protobuf 내부 계약) 소관이다.
- **하류 파급**:
  - ADR 0004(persistence·events)가 DB 기반 스케줄·outbox를 기록한다.
  - **capability OPS-06(queue topology 배포 게이트)이 재정의된다** — 브로커 존재를
    전제한 capability이므로 0B·0C에서 "DB 기반 큐의 배포 게이트"로 다시 쓰거나 폐기한다.
  - `OPEN-OPS-03`(큐 깊이 SLO)의 입력이 "1인 운영"으로 확정됐다 — 실시간 경보가 아니라
    다음 접속 시 확인 가능한 형태로 설계한다.
  - legacy `consumer_timeout` 유도 관계(operations 노트 §C-02)는 무의미해진다.

### OPEN-STR-01 · 운영자 예산 필터가 비교하는 금액의 basis — **결정: (c) + 기초금액**

- **결정**: basis를 운영자가 지정하는 1급 필드로 승격하고, V2는 값과 basis 태그를 함께
  저장·비교한다. **기존 저장 값은 기초금액으로 해석한다.**
- **운영자 답**: 예산 필터에 적은 값은 **기초금액**이다(2026-08-26).
- **이 답이 만든 판정 — `legacy-defect`**
  - legacy는 운영자 값을 **추정가격**과 비교한다:
    `app/services/opportunity_monitoring/filters.py`
    `project_budget = float(project.budget_estimate or 0.0)` ↔
    `strategy.min|max_budget_estimate`. `Project.budget_estimate`는 추정가격(ex-VAT)이다
    (strategy 노트 OPEN-1).
  - 운영자 의도가 기초금액이므로 **legacy는 운영자가 지정하지 않은 basis로 필터한다.**
    기초금액과 추정가격은 VAT·사정률만큼 체계적으로 다르므로 임의 오차가 아니라
    경계 근처 공고를 **한 방향으로 일관되게** 누락/포함시킨다.
  - **같은 결함 부류가 이미 한 번 고쳐져 있다.** R-07(#162 계열)에서 capture 점수 분모가
    추정가격이라 과세 공고의 점수가 부풀던 것을 `resolve_notice_bid_base`(기초금액)로
    바꾸고 `BaseAmount` 뉴타입으로 교차 대입을 정적 차단했다(commit `0755695`).
    **capture 경로는 고쳤고 예산 필터 경로는 고치지 않았다.**
- **하류**:
  - 0C 데이터 사전이 예산 필터 필드의 basis를 `기초금액`으로 명시하고 basis 태그 필드를 정의한다.
  - 0B regression ledger에 이 항목을 추가한다 — 관찰·사용자 영향·V2 예방 제약
    (basis는 타입이다 / `BaseAmount` 뉴타입 상당물)·검증 방법·근거가 전부 확보돼 있다.
  - M1 도메인 커널이 basis 교차 대입을 타입으로 차단한다.
  - **마이그레이션**: 기존 운영자 전략 값은 basis 태그 없이 저장돼 있으므로, 이 결정을
    근거로 `기초금액`으로 일괄 태깅한다. 이 결정 없이 늦게 채택했다면 구제 불가였다.

### OPEN-ML-04 · 정산 관측 시각을 canonical fact로 — **결정: 넣는다**

### OPEN-NUM-04 · ML 실측 수치의 fixture 계층 — **결정: (a)**

- 출력 수치는 전부 `legacy-behavior`, 입력 형태·경계 조건만 `observed`로 승격.
- **승격되는 것은 형태이지 건수가 아니다.** "69행", "91.9%", "n=1,405" 같은 모수는
  승격 대상이 아니며 fixture에 인용하지 않는다.
- 근거: `data-extract.md` §1의 계층 정의와 일치한다. 사용자 판단이 아니라 문서가 이미
  정한 분류였다.

### OPEN-QUAL-06 · `Uncertain` 판정의 분해 — **결정: (a)**

- 분포 재측정 없이 sealed subtype으로 분해한다. 비율은 V2 운영 관측으로 산출한다.
- **사유 enum은 legacy evidence 문자열을 옮기는 것이 아니라 도메인 명세가 먼저 정하고
  구현이 따른다**(ML-11.4 F7의 교훈). scout 노트의 4분류는 후보이지 확정 목록이 아니다.
- 근거: `v2-지침서.md` §4.2가 `Uncertain(reasons)`의 구조화를 이미 요구한다. 분포는
  분해 여부를 바꾸지 않고 우선순위만 바꾼다.

### OPEN-DEC-08 · legacy `clean` 라벨 — **결정: (b)**

- legacy `clean` 라벨을 V2 corpus에 승계하지 않는다. write provenance를 갖고 새로
  수집·판정한 행만 clean으로 인정하고, legacy에서 가져오는 행은 provenance 미상으로 격리한다.
- 후속 확인: 런북의 3,982건 코호트 쿼리가 legacy DB 접근 없이 재현 가능하면 (a)로 좁힌다.
- 근거: 런북 자신이 "legacy 데이터만으로는 오염 행과 정상 clean 행을 구분할 수 없다"고
  적는다 — 표식이 값이 아니라 write 경로인데 legacy엔 provenance가 없다.

### OPEN-OPS-07 · 운영 라이브러리 6종 조회 — **결정: (a). 조회 착수**

- **필수 단서(단서 없는 (b)는 현재 결함을 이식한다)**: legacy의 "명시 제외"는 docstring
  한 줄뿐이고 **런타임에는 지자체가 국가계약 tier로 판정된다**
  (`floor_applicability.py:125-126`; `tests/test_floor_applicability.py:70`이
  "울산광역시 울주군"→`FLOOR_APPLICABLE`을 고정). 그 결과 얕은 하회 0.9~2.7%p가 legacy
  자신의 백테스트 문서에 한계로 공시돼 있다.
- **따라서 V2는 "실행되는 미적용 상태"로 구현한다** — 지자체 공고를 국가계약 하한으로
  조용히 판정하지 않고, 하한 체계 미지원을 **관측 가능한 상태**로 산출한다.
- **0B 인계**: 이 항목은 regression ledger 대상이다(선언과 실행의 불일치).

### OPEN-STR-05 · 텍스트 매칭 의미 — **결정: (a) 부분문자열 유지**

- **운영자 답**: 현재 키워드 필터의 오탐 경험이 없다(2026-08-26).
- 근거: 바꾸면 오탐 특성이 전면 재검증 대상인데, 변경을 요구하는 관찰이 없다.
- **잔여 주의**: 오탐 부재는 운영자 체감이며 측정치가 아니다. V2에서 매칭 결과가
  관측 가능해지면(어떤 규칙이 왜 걸렸는지) 그때 재평가할 수 있다. 이 결정이 재평가를
  막지 않는다.

### 파급 — 0A 동결 중 발견된 M-4가 해소된다

`OPEN-DEC-05`가 "하나의 `Skip` + 필수 reason code"로 확정되면서, verifier 라운드 6이
찾은 **M-4**(`capability-map.md:1360` DEC-12 A9 표 셀이 "하나의 verdict가 두 뜻을 겸함"을
채택 금지 구조로 등재해 `OPEN-DEC-05`의 (a) 분기를 배제)가 **결함이 아니게 된다** —
결정이 내려졌으므로 확정 서술이 허용된다. 다만 A9 셀은 **reason 문장으로만 구분되는
형태**를 금지하는 것으로 문면을 정확히 해야 한다(reason **code**는 이번 결정이 채택했다).
통합 패스에서 처리한다.

## 2026-08-26 — M1 잔여 3건 + 상호작용 모델 확정

### OPEN-DEC-01 · 하한 미달 빈도 최소 표본 수 150 — **결정: (a) 유지 + 통계적 편의로 명시 승인**

- **운영자 답**: 150을 유지하고 근거를 "통계적 편의"로 명시 승인한다(2026-08-26).
- 도메인 요구가 아님이 확정됐으므로, V2는 이 값을 **정책 데이터로 외부화하고 근거 문자열을
  "통계적 편의(운영자 승인 2026-08-26)"로 기록**한다. 코드에 상수로 묻지 않는다.
- `OPEN-DEC-07`(마진 재유도)과 달리 이 값은 재유도 대상이 아니다.

### OPEN-DEC-04 · 운영자 하한 override의 상한 검증 — **결정: (c) 사유와 함께 거부**

- **운영자 답**: 거부를 수용한다(2026-08-26).
- 개연 밴드 밖 override는 **버리지도 통과시키지도 않고 사유와 함께 거부**한다.
- legacy는 "명시적 지시를 조용히 버리지 않는다"는 이유로 검증을 걸지 않고 위험을 스스로
  공시했다. V2는 조용히 버리지 않는다는 원칙을 유지하되 **거부를 관측 가능한 결과로** 만든다.

### OPEN-STR-06 · 채널 배달 게이트 임계 — **결정: (a) 운영자 전략으로 승격**

- **운영자 답**: 승격한다(2026-08-26).
- 아래 상호작용 모델과 정합한다 — 채널이 "지금 투찰해야 하는 것"만 받는 통로이므로
  그 임계는 시스템 설정이 아니라 **운영자의 긴급도 판단**이다.

### OPEN-NOTI-02 · 중복 알림 vs 놓친 알림 — **결정: at-most-once (놓침을 감수)**

- **운영자 답**: 앱 알림함이 놓친 것을 회수하는 경로가 맞다(2026-08-26).
- **내구성 요구가 채널에서 앱 알림함(DB)으로 이동한다.** 채널 배달은 실패 시 버리되,
  앱 알림함은 누락이 없어야 하고 마감 임박 건을 사후에 조회할 수 있어야 한다.
  이 조건이 깨지면 놓친 알림 = 놓친 투찰이 된다.
- **`OPEN-STR-08`(직전 run 실패 시 중복 억제)이 함께 정리된다** — 중복이 싸고 놓침도
  감수 대상이므로 재발송이 안전한 기본값이다. 억제는 앱 알림함(NOTI-10)이 소유한다.

### 상호작용 모델 — **pull 확정** (운영자 진술, 2026-08-26)

> "관심 있는 입찰건을 모두 알림받아 운영자가 강제 처리해야 하는 시스템이 아니다.
> 시스템은 입찰 조건에 맞으면 제안하고, 투찰가를 요청하면 제시하면 된다. 사업자는
> 언제든 입찰 목록에서 관심사·제목 등으로 검색하고 투찰가를 요청할 수 있다."

확정되는 것:

1. **주기 감시는 후보를 제안까지만 한다.** 수집 → 조건 매칭 → 제안 목록. (STR-09·STR-08 유지)
2. **투찰가 산출은 on-demand다.** legacy는 파이프라인 run에서 배치로 산출한다
   (lineage stage `selected → workload → decision → notification → completed`).
   **V2는 요청 시 산출한다.** 이는 legacy 복제 금지 원칙에 따른 의도적 재설계다.
3. **운영자에게 강제되는 작업 큐가 없다.** 워크플로 상태 기계가 "운영자가 처리해야 할 항목"을
   추적할 필요가 없다.

**하류 파급:**

- **M2 계약**: 투찰가 산출이 request/response가 된다 — 운영자의 gRPC + callback 방향과 일치.
- **M5 serving**: 배치 선산출 부하가 사라지고 요청 단위 지연이 설계 기준이 된다.
- **큐 폭주 문제의 뿌리가 사라진다.** legacy OPS-00의 21,321건은 배치 산출 작업이 쌓인 것이다.
  `OPEN-OPS-03`(큐 깊이 SLO)의 모수가 근본적으로 달라진다.
- **capability 재분류 후보**(통합 패스에서 처리, 임의 변경 금지):
  | capability | 현재 | 후보 | 사유 |
  | --- | --- | --- | --- |
  | NOTI-06 채널 인바운드로 판단 처리 | `V2 필수` | **후속** | 알림 버튼으로 판단을 기록하는 push 상호작용. pull 모델의 주 경로가 아니다 |
  | NOTI-02 알림 피로도 게이트 | `V2 필수` | **후속 또는 축소** | 알림을 다 소비하지 않아도 되므로 피로도 억제의 가치가 크게 낮다 |
  | NOTI-05 배달 outbox | `V2 필수` | **후속** | best-effort 배달이면 "커밋 후에만 보낸다"로 충분 |
  | NOTI-10 앱 알림 중복 억제 | `V2 필수` | **유지·강화** | 앱 알림함이 기록이자 회수 경로로 확정됐다 |
  | DEC-02 추천 투찰가 산정 | `V2 필수` | **유지, 산출 시점 변경** | 배치 → on-demand |

- **capability 누락 발견 (신규)**: **운영자가 입찰 목록을 관심사·제목으로 검색하고 투찰가를
  요청하는 경로가 capability map에 없다.** 전수 확인 결과 검색·목록 관련 항목은 COL-01
  (수집)과 QUAL-10(무관)뿐이다. pull 모델에서 이것이 **운영자의 주 경로**이므로
  `milestone-0.md` 완료 조건("V2 필수 capability마다 사용자 가치와 acceptance scenario")에
  직접 걸린다. 조사가 legacy(push·batch 모델) 기반이라 구조적으로 빠진 영역이다.
  **신규 capability로 추가해야 한다** — 통합 패스 또는 0B에서 처리.
