## 2. A2 — 미결 OPEN 임의 해소 **0건** (이 slice의 실패 조건)

```
소멸 29건 / 신규 0건
결정 기록에 없는데 소멸(=임의 해소): 0건
결정 기록에 있는데 잔존: 0건
OPEN-OPS-03 잔존: True
```

- **id 집합을 양방향으로 대조했다** — 수치가 아니라 집합이다. 전체 출력은 `commands.md` A2.
- **`OPEN-OPS-03`은 해소하지 않았다.** 입력("1인 운영")만 부분 확정이고 임계는 미결이다.
  §12.2의 "해소되지 않은 인접 항목" 표에 사유를 적었다.
- 같은 표에 **`OPEN-OPS-01` · `OPEN-NUM-02` · `OPEN-SET-06` · `OPEN-NOTI-01` ·
  `OPEN-NOTI-08`**이 왜 인접 결정에도 불구하고 열려 있는지 적었다 — 이 다섯은 해소된
  항목과 축이 겹쳐 혼동되기 쉬운 것들이다.

## 3. A3 — 신규 capability

**STR-16 · 입찰 목록 검색과 투찰가 요청 (운영자의 주 경로)**, 분류 `V2 필수`.

| 요구 | 충족 |
| --- | --- |
| `V2 필수` 분류 | 있음 |
| 사용자 가치 | 있음 — "언제든 목록을 검색하고 고른 공고의 투찰가를 요청해 즉시 받는다" |
| acceptance scenario | **6항목** — 검색 범위(감시 조건과 무관), on-demand 산출, 판정 불가의 사유 있는 답, 같은 입력 같은 답, read-only, 빈 결과의 2분 |
| 분류 근거 | 있음 — **legacy 관찰이 아니라 운영자 진술**임을 명시했다 |

**분류 근거를 지어내지 않았다.** legacy에 대응 구현이 없으므로(전수 확인: 검색·목록
관련은 COL-01(수집)·QUAL-10(무관)뿐) 근거를 **운영자 진술 2026-08-26**으로 적고, 이
항목이 "조사가 legacy(push·batch) 기반이라 구조적으로 빠진 영역"에서 나왔다는 사실을
본문에 남겼다. 이 문서의 다른 94개와 근거의 성격이 다르다는 점을 명시한 것이다.

**축 배정**: STR. 사유는 §0.6의 STR 소유 주제가 "감시 조건, 임계치, **후보 산출 트리거**"
이고 이 항목이 운영자가 직접 거는 후보 산출 트리거이기 때문이다. 새 축을 만들지 않은
이유(전략 축의 **수동 경로**이지 별개 주제가 아니다)도 본문에 적었다. id는 STR 축의 다음
번호 `STR-16`이다.

## 4. A4 — capability 재분류 5건과 §10 집계 일치

| capability | 이전 | 현재 | 근거 |
| --- | --- | --- | --- |
| NOTI-06 채널 인바운드로 판단 처리 | `V2 필수` | **`후속`** | 알림 버튼 판단 기록은 **push 상호작용**이며 pull의 주 경로가 아니다 |
| NOTI-02 알림 피로도 게이트 | `V2 필수` | **`후속`** | 알림을 다 소비하지 않아도 되므로 피로도 억제의 가치가 크게 낮다 |
| NOTI-05 배달 outbox | `V2 필수` | **`후속`** | at-most-once 확정 + best-effort면 "커밋 후에만 보낸다"로 충분 |
| NOTI-10 앱 알림 중복 억제 | `V2 필수` | **`V2 필수` 유지·강화** | 앱 알림함이 **기록이자 회수 경로**로 확정 — 내구성 요구가 채널에서 여기로 이동 |
| DEC-02 추천 투찰가 산정 | `V2 필수` | **`V2 필수`, 산출 시점 변경** | 배치 → **on-demand** |

**NOTI-02의 "후속 또는 축소" 선택**: **후속**을 택했다. 사유 — 축소는 "기능을 줄여
남긴다"인데, pull 모델에서 낮아진 것은 규칙의 정교함이 아니라 **피로도 억제 자체의 가치**다.
규칙 구조(정렬된 rule table + 첫 위반 승)의 재사용 가치는 그대로이므로 잘라낼 부분이 없고,
바뀐 것은 **언제 필요한가**다. 따라서 시점 이동(후속)이 정확하다. 재사용 가치가 유지된다는
사실은 분류 줄에 함께 적었다.

**§10 재계산**: `62 / 17 / 6 / 10 = 95`. 축별 표를 갱신하고 **변경 표와 순증감 사유**를
같은 절에 기입했다(`commands.md` A6/A4 절과 동일 수치).

**`OPS-06`(queue topology 배포 게이트)**: `OPEN-OPS-05`(브로커 없음) 확정으로 **전제가
사라졌다**. §13에 "DB 기반 큐의 배포 게이트로 재정의하거나 폐기한다"를 기록했고,
**재정의 자체는 하지 않았다** — 근거가 아직 존재하지 않는 DB 큐 설계에 종속되기 때문이다.

## 9. 알려진 제한

1. **`OPS-06` 재정의를 하지 않았다.** 브로커 없음 결정으로 전제가 사라진 것은 기록했으나,
   대체 정의("DB 기반 큐의 배포 게이트")를 쓰려면 DB 큐 설계가 있어야 하고 그 설계가 아직
   없다. §13 인계로 남겼다.
2. **STR-11의 분류를 올리지 않았다.** `OPEN-STR-11`이 해소됐음에도 `근거 부족`을 유지한다 —
   닫힌 것은 `OPEN-STR-07` 의존 축이고, 이 블록의 분류 근거인 "운영자 실사용 여부"에 대한
   판단이 **결정 기록에 없다**. 기록에 없는 것을 결정하지 않는다. **후속 결정 대상**이며
   이 slice가 만든 문제가 아니라 드러낸 문제다.
3. **잔여 활성 OPEN 37건.** M0·M1 차단은 전부 해소됐으나 G2(정책 값 재유도)·G4(legacy
   의도 판정)·G5(수치 재측정)가 남아 있고 다수가 V2 코퍼스나 운영 관측을 선행 조건으로
   갖는다. `milestone-0.md` 완료 조건은 "`OPEN` 0개이거나 사용자 명시 승인"이다.
4. **축의 한계는 0A가 기록한 그대로다.** F1·F2'·X는 대리 지표 기반 triage 필터이며
   계열 A의 부재를 증명하지 않는다(`reports/evidence/m0/0a/checklist.md` §11.3).
   0A2가 이 한계를 뒤집지 않는다. 다만 활성 OPEN을 66 → 37로 줄여 **계열 A의 표면 자체를
   44% 줄였다** — 축이 아니라 결정이 그 일을 했다.
5. **이월(0A에서 넘어온 것, 변동 없음)**: 라운드 1 verifier L-4~L-6, 라운드 0 F-5,
   라운드 5 L-4(라운드 3 E1~E4·라운드 4 F2 스크립트 미기입).
