## 리뷰 요청 조건 (evidence-pack)

- [x] 구현 diff 커밋됨 — `git status --porcelain -- <in_scope 개별 인자>` 빈 출력. **양성 대조**: 음성
      대조 ①~⑤ 가 매번 `git diff --numstat` 으로 실제 변경을 수치로 냈고 복원 뒤 빈 출력으로 돌아왔다
      (더러운 트리와 깨끗한 트리가 구별됨을 같은 명령으로 보였다). 복원은 `checkout --` 이 아니라
      **변이 전 사본 덮어쓰기**로 했다(미커밋 편집을 함께 지우지 않는다)
- [x] acceptance 전부 exit 0 — commands.md. `check` 는 **한 번 exit 1 을 거쳤다**(이 레인이 같은
      워크트리에서 빌드 두 벌을 겹쳐 띄운 실행 실수 — 테스트 워커가 끊겼고 리포트조차 생성되지
      않았다). 단일 빌드로 재실행해 exit 0. 실패 이력을 지우지 않고 남긴다 — 그 줄이 「무엇이
      측정을 무효로 만드는가」를 다음 라운드에 전한다
- [x] 전건 게이트 — `container` job 전부 + Kotlin `check` 전건(부분 게이트로 줄이지 않았다)
- [x] 정책 version 근거 — `vuln-policy.properties` 는 신설이라 `policy.version=1`. 도구 판 선택 근거는
      commands.md 「도구 채택」 절
- [x] 알려진 제한과 rollback — 아래 · rollback.md
- [x] 비밀값 스캔 — 참조형으로 실행, 이 slice 가 쓴 파일에서 매치 0(commands.md)

## 알려진 제한

1. **서명 검증을 돌리지 않았다.** cosign 이 호스트·러너에 없어 trivy 자산의 sigstore 서명을 암호학적으로
   검증하지 못했다(인증서 문면 — 발급자·소스 저장소·ref·빌드 커밋·서명 시각 — 확인까지). 구속력 있는
   잠금은 저장소에 핀한 체크섬이다. cosign 을 들이는 것은 **또 하나의 공급망 축을 더하는 결정**이라
   운영자 판단 영역으로 남긴다(`OPEN-6E2B-TOOL-SIGNATURE-VERIFICATION`).
2. **게이트가 재는 것은 「방금 만든 로컬 이미지」다.** 배포본과 같은 바이트라는 보증(서명·다이제스트
   승격·레지스트리 push)은 없다. 6C 에서 이어받은 경계이고 이 slice 가 좁히지 않았다.
3. **취약점 DB 를 실행마다 받는다**(B-5 (a)). 저장소를 건드리지 않은 PR 이 새 CVE 공시만으로 붉어질 수
   있다 — 게이트의 목적이지만 **무관한 PR 이 치르는 비용**이므로 제한으로 등재한다. 처방은 runbook §8.3.
4. **네트워크 의존이 셋 늘었다** — 릴리스 자산 다운로드 · 취약점 DB · **Java DB**(jar 층 판정에
   따로 받는다, 요약의 `trivy version` 출처와 같은 자리에서 확인된다). 레지스트리·네트워크 접근이
   없는 환경에서는 이 게이트가 판정 불가로 실패한다(위생 게이트의 베이스 다이제스트 축과 같은 성질).
5. **셸 게이트 정책 파서가 둘이 됐다.** `tools/image-hygiene-check.sh` 의 `_policy_value` 와 같은 설계를
   이 스크립트가 다시 갖는다 — `OPEN-6C-POLICY-GATE-STRUCTURAL`(셸 정책 파싱을 build-logic 타입
   태스크로)의 **모집단이 1 에서 2 로 늘었다**. 지금 공유 라이브러리로 뽑지 않은 것은 그 추출이 검증된
   6C 게이트를 이 slice 범위 밖에서 건드리기 때문이다.
6. **「게이트가 돌았는가」는 셸 종료 코드뿐이다** — 위생 게이트와 같은 기존 한계를 이 게이트도 진다.
7. **멀티아키를 보지 않는다**(`OPEN-6C-MULTIARCH`) — 빌드한 플랫폼의 이미지만 잰다.
8. **오늘의 등재 67 은 전부 상향 대기다.** 하나도 「영향 없음」 판단이 아니다 — 전부 올리면 사라지는
   것이고, 올리는 일은 D-6E2B-1 로 후속 slice 6E-2c 가 진다. 그때까지 **tomcat-embed-core 의 CRITICAL
   셋을 포함한 10건이 열린 채 돈다** — 이 slice 가 더하는 것은 그 사실의 가시성과 기한이지 수정이 아니다.
9. **`scan.min-packages` 하한은 kind 당 하나의 수치다.** 양성 대조로 「아무것도 못 읽음」은 잡지만,
   스캐너가 **일부 생태계만** 놓치는 경우(예: jar 층만 비는 경우)는 잡지 못한다. 양성 대조에서 실제로
   보인 성질이다 — 다른 이미지를 같은 kind 로 재니 구성요소 85 로 하한 80 을 간신히 넘었다.

## 이 slice 가 겪은 측정 함정 둘 (다음 라운드로 넘길 것)

1. **측정 중에 트리가 움직이면 exit 0 은 아무 트리도 설명하지 못한다.** 첫 회차 체인은 시작 시점의
   HEAD 를 읽어 두었는데 그 뒤 산출물 커밋이 셋 붙었다(팀장의 계약 갱신 포함). 결과는 폐기했고,
   **트리를 고정한 뒤** 다시 돌렸다. 시작 HEAD 를 읽는 것만으로는 모자라다 — rollback.md 의 verifier
   술어(`git diff --name-only <실측 HEAD>..<판정 SHA> -- <되돌림 경로>`)가 바로 이 축을 잰다.
2. **대기 장치를 겹쳐 두면 둘 다 발화한다.** 호스트 슬롯 grabber 를 둘 띄워 둔 탓에 같은 워크트리에서
   `check` 가 두 벌 돌았고, 정리 과정에서 한쪽 워커가 끊겨 `:app:test` 가 `EOFException` 으로 떨어졌다.
   「호스트 전체 무거운 빌드 1개」 규율은 **다른 레인과의 사이뿐 아니라 자기 자신과의 사이에서도**
   지켜야 한다.
