**app 의 ID 가 바뀌었다 — `origin/main` 병합 때문이다.** 6E-2a 의 production 코드(풀·역할)가 들어오면서

**이 ID 는 「이 회차가 판정한 바이트」다.** 이 호스트는 두 태그를 레인끼리 공유하고, app 태그는 실제로
`a5edaf3e…` ↔ `aaeb2502…` 로 오갔다 — 태그만 적은 기록은 무엇을 쟀는지 말하지 않는다. **트리별
재현성은 주장하지 않는다**: 관측이 더운 layer 캐시 위에서 났고 캐시 적중은 ID 를 구성적으로 재현하므로,
`--no-cache` 없이는 서지 않는다(그 비용은 쓰지 않기로 했다).

**어느 DB 로** — trivy `0.75.0`:

  ml-serving 회차에서는 `unknown`(요구하지 않으므로 받지 않는다 — kind 별 선언이 실제로 갈린다)

**이 계수가 evidence 안의 유일한 출처다**(PR #68 /code-review). 다른 자리에서 같은 수를 다시 적지 않는다 —
대조표도 「하한 미만」까지만 말하고 수치는 그 실행의 요약 줄이 낸다. **이미지를 다시 빌드하면 한두 개
움직인다**(레인끼리 태그를 공유하므로 실제로 225↔226 을 오갔다). 정책 파일의 하한 근거 주석은 **그 날의
실측**이고 이 줄과 몇 개 다를 수 있다 — 하한은 약 2/3 로 잡혀 그 차이에 둔감하다.

**DB 시각이 라운드마다 다른 것이 정상이다** — 캐시를 샌드박스에 고정한 뒤로 실행마다 새로 받으므로,
같은 커밋을 다시 재면 그때의 상류 DB 로 판정한다. 「같은 수치가 나왔다」가 아니라 **「그날의 DB 로 쟀다」**
가 이 줄의 뜻이다.

### CI step 조건 — 평가기 실측(신설 M-1)

워크플로의 `if` 를 그대로 평가해 **원인 하나에 빨강 하나**인지 쟀다(평가기는 verifier 것을 읽기 전용으로
복사). 조치 전: install 실패에 **빨강 셋**(install · 조건이 install 을 안 보던 S-22e · 올릴 파일 없는 S-22f).

| 실패 step | 조치 후 |
|---|---|
| `install trivy` | install 만 FAIL · S-22d·S-22e·S-22f **전부 skip** |
| S-22d(ml 스캔) | S-22d FAIL · **S-22e 는 그대로 돈다**(M-3 결정 보존) |
| S-22b(앱 위생) | S-22b FAIL · 뒤 전부 skip |

**이동이 실제로 살리는 것은 S-21~S-22c 뿐이다.** S-23~S-24 는 `if` 가 없어 암묵 `success()` 라 여전히
건너뛴다 — 6E-2b 이전과 **같은 결합**이고 이 이동이 고치는 축이 아니다(앞 보고의 주장을 좁힌다).

A2 는 **고친 커밋의 부모(`49f7c8e5~1`)를 그대로 돌린 것**이다. 손으로 만든 「옛 형태」 사본으로는 재현되지
않았다 — 원래 코드는 배열을 `printf` 로 펴서 **여러 번 쓰고**, 내 사본은 문자열 하나를 한 번에 써서
SIGPIPE 를 덜 탔다. **대조군은 재구성이 아니라 그 커밋이어야 한다.**

F 가 번진 곳은 **보관 SBOM 하나다**(verifier 표적4 L-A 정정). 앞서 나는 「스캔이 그 SBOM 을 입력으로
쓰므로 필터가 판정까지 번진다」고 적었는데 **실측과 다르다** — 같은 대조에서 `trivy sbom` 단계의 finding 은
**50, exit 0** 이었다. `trivy sbom` 은 SBOM 의 `vulnerabilities` 칸이 아니라 **구성 요소 목록을 DB 와 다시
맞추므로**, SBOM 에서 취약점을 지워도 판정은 그대로다.

**그래도 고치는 것이 맞다**: artifact 가 판정 대상과 같은 물건이어야 한다는 **B-1 의 약속**이 깨지기
때문이다(보관본만 finding 을 잃는다). 사유를 그 자리로 좁힌다 — 「판정까지 번진다」가 아니라
**「보관 SBOM 이 finding 을 잃는다」**.
