# M6/6B-2 백업·복원·마이그레이션 되돌림 runbook (초안 2026-10-05)

> 정본 계약: `reports/evidence/m6/6b2/scope.md`(D-6B2-1~3). 이 문서는 **절차**만 담는다 — 값의 근거는 그 계약과
> `_workspace/m6-6b2/00_scout.md` 의 착수 실측에 있고, 실행 결과는 `reports/evidence/m6/6b2/commands.md` 에 적는다.
> 절차의 모든 명령은 `tools/db-backup.sh` · `tools/db-restore.sh` · `tools/db-rehearsal.sh` 셋과 1:1 이다.

## 0. 두 축을 섞지 않는다

| 사고 | 정본 절차 | 데이터 손실 | 왜 |
|---|---|---|---|
| **스키마를 잘못 올렸다** — 마이그레이션을 되돌려야 한다 | **forward-fix**(§1) | 없음 | 마이그레이션 15 개(V17 까지)가 전부 추가 전용이라 되돌림이 비파괴다 |
| **데이터를 잃었다** — 지워졌거나 망가졌다 | **백업 복원**(§3) | 마지막 백업 이후분 | 논리 백업이 유일한 되돌림 수단이다 |

**「되돌림 = 백업 복원」이 아니다.** 스키마 되돌림에 백업 복원을 쓰면, 고칠 필요가 없던 데이터까지 마지막 백업
시점으로 되감긴다. 두 축은 쓰는 자리가 다르고 비용이 다르다.

## 1. 되돌림 정책 — forward-fix 가 정본

| 상태 | 되돌리는 법 |
|---|---|
| 아직 적용되지 않은 DB | 그 `V<n>` 파일을 **지운다** |
| 이미 적용된 DB | **새 `V<n+1>` 파일**이 역 DDL 을 담는다(`ALTER TABLE … DROP COLUMN` 등). 앞 파일은 건드리지 않는다 |

- **이력은 지우지 않는다.** 되돌린 뒤 `flyway_schema_history` 에는 사고를 낸 버전과 그것을 되돌린 버전이 **둘 다
  남는다.** 그것이 forward-fix 의 성질이고 결함이 아니다 — 적용된 체크섬을 사후에 바꾸지 않기 때문에 다른 환경의
  `validate()` 가 깨지지 않는다. 리허설 (i) 가 이 성질을 매 PR 에 실측한다.
- **Flyway community 판에는 `undo` 가 없다.** 역 SQL 파일(`U*.sql`)을 만들지 않는다 — 이 저장소에 0 건이고
  그대로 둔다.
- **`clean` 은 구성상 불가하다.** `PersistenceWiring.migrate()` 가 전부 기본값으로 Flyway 를 부르므로
  `cleanDisabled` 가 켜져 있고 호출자도 없다. 「DB 를 비운다」는 Flyway 로 할 수 없고, 리허설은 **컨테이너·볼륨
  폐기**로만 한다.
- 되돌림 문장은 새 마이그레이션의 머리 주석에 그 자리에서 적는다(`V16`·`V17` 이 선례다).

## 2. 백업 절차

```
./tools/db-backup.sh <postgres 컨테이너> <출력 디렉터리> [<데이터베이스>]
```

| 산출물 | 무엇 |
|---|---|
| `roles.sql` | 클러스터 역할 — `pg_dumpall --roles-only --no-role-passwords` |
| `db.dump` | 스키마·데이터 — `pg_dump --format=custom` |
| `manifest.json` | 산출물 sha256 둘 + **복원 등식의 재료** `measurements` 열 가지 |

- **자격 값을 주지 않는다.** 접속은 전부 `docker exec` 로 컨테이너 안 유닉스 소켓을 지난다(공식 postgres 이미지의
  `pg_hba.conf` 가 소켓 줄을 `trust` 로 둔다). 슈퍼유저·DB 이름은 컨테이너 자신의 `POSTGRES_USER`·`POSTGRES_DB`
  에서 읽는다. 값이 호스트 argv·환경·로그 어디에도 실리지 않는다.
- **역할 암호는 백업에 담기지 않는다.** 맨 `pg_dumpall --roles-only` 은 로그인 역할의 SCRAM 검증자를 평문 파일에
  적는다 — 백업 파일을 복사하는 모든 사람에게 오프라인 공격 재료를 주는 셈이다. `--no-role-passwords` 가 그 줄을
  빼고, 복원이 필요로 하는 역할의 **존재·속성·소속**은 그대로 담긴다(`bidvector_app` 은 NOLOGIN 이라 애초에 암호가
  없다). **대가**: 복원한 클러스터의 로그인 역할은 암호가 없는 상태로 선다 — 운영 복원에서는 복원 직후 운영자가
  별도 경로로 암호를 설정해야 하고, 그 값은 이 절차가 만드는 어떤 파일에도 들어가지 않는다.
- 백업본을 **저장소 안에 두지 않는다.** 저장 위치·보존 기간·암호화는 이 slice 가 정하지 않는다(§7).

## 3. 복원 절차

```
./tools/db-restore.sh <백업 디렉터리> <대상 컨테이너> <이미지> <새 데이터베이스> <실행 표식>
```

순서가 중요하다 — **역할 → 데이터베이스 생성 → 스키마·데이터 → 등식**.

1. **백업 무결성**: `manifest.json` 이 적은 sha256 과 실제 파일을 맞춘다. 다르면 거기서 멈춘다.
2. **역할 먼저**: `pg_dump <db>` 는 역할을 담지 않는다 — 역할은 **클러스터** 객체이고 덤프에는
   `GRANT … TO bidvector_app` 만 들어 있다. 새 클러스터에 역할이 없으면 그 GRANT 가 **전부** 실패한다.
   이미 있는 역할의 `CREATE ROLE` 은 정상적으로 실패하므로, 판정은 명령의 종료 코드가 아니라 **manifest 가 적은
   역할이 전부 존재하는가**다.
3. **새 빈 데이터베이스**: 원본의 소유자·인코딩·collation 그대로 만든다. 이미 있으면 거부한다 — 비어 있지 않은
   스키마에 이력 표 없이 복원하면 다음 기동에서 Flyway 가 거부한다.
4. **스키마·데이터**: `pg_restore --exit-on-error`.
5. **등식**: 복원본을 `db-backup.sh` 로 **다시 재어** 원본 manifest 와 측정 단위로 맞춘다.

| 측정 | 무엇을 잡는가 |
|---|---|
| `database` | 소유자·인코딩·collation |
| `flywayHistory` | 이력 행 수·최상위 버전·**행 집합 해시** |
| `tables` | 표별 행 수 + 정렬된 행 전체의 sha256 |
| `columns` | 표별 열 구조(빈 표의 열 손실은 내용 해시로 안 잡힌다) |
| `sequences` | IDENTITY 현재값 — 다음 INSERT 가 충돌하지 않는가 |
| `roles` | 역할 존재와 속성 |
| `privilegeMatrix` | 축9 유효 권한 행렬(직접 부여·PUBLIC 부여·역할 상속 해소) |
| `functions` | 소유자와 `SECURITY DEFINER` 여부 |
| `triggers` · `constraints` | 가드 트리거와 CHECK 정의 |

어긋나면 **어느 등식의 어느 이름**인지 한 줄로 댄다:
`등식 어긋남: privilegeMatrix / bidvector_app — 원본 … · 복원본 …`

두 manifest 만 비교하려면(무시할 측정을 쉼표로 줄 수 있다):

```
./tools/db-restore.sh --compare <원본 manifest> <복원본 manifest> [<무시할 측정>]
```

**Flyway `validate()` 는 이 스크립트가 부르지 않는다.** `flyway_schema_history` 의 행 집합 해시 등식이 그 자리에
선다 — validate 는 이력 행과 마이그레이션 파일 체크섬만 보는 순수 함수이므로, 같은 checkout 에서 이력 행이 같으면
답도 같다. 운영 복원에서 실제 validate 를 도는 것은 **앱 기동**이다(`validateOnMigrate` 가 기본값으로 켜져 있어
이력과 파일이 어긋나면 기동이 거부된다).

**대상은 자기 자원뿐이다.** 대상 컨테이너가 이미 있으면 `bidvector.rehearsal` 라벨이 **존재하고** 그 값이 준
실행 표식과 같을 때만 손대고, 없으면 그 라벨을 붙여 직접 만든다. 존재와 값을 함께 묻는 이유는 없는 라벨을 묻는
조회가 빈 문자열을 돌려주기 때문이다 — 그래서 **비거나 공백뿐인 실행 표식은 인자 검사에서 거부한다.** unset
변수 하나가 그 인자를 만들면 라벨이 아예 없는 남의 컨테이너가 등식을 통과한다. 만든 컨테이너는
`--network none` 이고 호스트 포트를 publish 하지 않는다.

## 4. 리허설 실행법

**CI** — `container` job 의 S-23c 가 매 PR 에 돈다. 자리는 **S-23b 와 S-24 사이**다: S-23b 의 쓰기 왕복이 남긴
`candidateLimit=13`·`revision+1` 이 데이터 손실 축의 재료이고, 그 행이 없으면 리허설이 「쓰기 왕복이 선행하지
않았다」로 끊는다 — step 순서가 단언으로 잠겨 있다.

**로컬** — 전제는 둘이다: compose 환경이 떠 있고 쓰기 왕복이 끝났을 것, 앱 이미지가 빌드돼 있을 것
(`./gradlew --no-daemon :app:bootJar` → `docker build -f docker/app.Dockerfile -t bidvector/app:local .`).

```
./tools/db-rehearsal.sh docker/compose.yaml postgres
```

| 리허설이 재는 것 | 판정 |
|---|---|
| **원본의 생성 출처** | 지목한 컨테이너의 `com.docker.compose.project.config_files` 라벨이 인자로 준 compose 파일의 realpath 와 같다. **프로젝트 이름 대조가 아니다** — 이름은 `COMPOSE_PROJECT_NAME`·`-p` 로 갈리므로, 같은 이름으로 뜬 남의 환경을 이름만으로는 배제하지 못한다. 자기 파일로 뜬 것만 통과하고 다른 파일의 컨테이너는 이름이 무엇이든 거부된다 |
| 백업 산출물의 누출 스캔 | `config/quality/leak-patterns.txt` 참조 스캔 0 건 |
| 복원 등식 | 측정 열 가지 전부 일치 |
| 복원본 Flyway `validate()` | 통과(출하본과 같은 Flyway·방언·드라이버, 설정 전부 기본값) |
| (i) forward-fix | 임시 V18 적용 → 임시 V19 로 되돌림 → 열이 사라지고 **이력에는 V18·V19 가 남는다** · 이력 밖 측정 전부 일치 |
| (ii) 데이터 손실 | 복원본의 전략 두 표를 지우면 등식이 **붉어지고**(음성 대조), 같은 백업으로 다시 복원하면 값이 돌아온다 |

임시 `V18`·`V19` 는 **커밋되지 않는다** — 리허설이 임시 디렉터리에 만들고 끝나면 지운다.
`adapters/src/main/resources/db/migration/` 에 남기면 clean DB 재현 등식(`CleanMigration*Test` 다섯)이 전부
붉어진다.

## 5. 멈춤 조건

| 증상 | 한다 | 하지 않는다 |
|---|---|---|
| 복원 등식이 `roles`·`privilegeMatrix` 에서 어긋난다 | 역할 복원이 먼저 돌았는지 본다 — 이 축이 가장 흔한 복원 실패다 | 권한을 손으로 GRANT 해 등식을 맞추기 |
| 복원 등식이 `sequences` 에서 어긋난다 | 덤프가 `setval` 을 담았는지 본다. 다음 INSERT 가 기존 키와 충돌할 수 있다 | 시퀀스를 임의 값으로 올려 넘기기 |
| `pg_restore` 가 GRANT 에서 실패한다 | 역할이 없는 것이다 — `roles.sql` 을 먼저 넣는다 | `--exit-on-error` 를 끄고 넘어가기 |
| 백업 산출물이 누출 스캔에 걸린다 | 그 자리에서 멈추고 산출물을 폐기한다 | 패턴을 좁혀 통과시키기 |
| 리허설이 만들 이름이 기존 컨테이너와 겹친다 | 멈춘다. 이름이 겹치면 남의 자원을 만질 수 있다 | 이름을 바꿔 다시 돌리기 전에 그 컨테이너가 무엇인지 확인하지 않기 |
| 리허설 컨테이너가 남아 있다 | `docker rm -f -v <이름>` 으로 치운다. 이름은 `<프로젝트>-rehearsal-6b2-…` 다. 리허설은 EXIT 트랩으로 자기 것을 지우지만 **치명 신호로 죽으면 트랩이 돌지 않고**(job 취소·`kill`), §3 의 단독 복원은 컨테이너를 **만들기만** 한다 | 라벨을 확인하지 않고 이름만 비슷한 컨테이너를 지우기 |
| 운영 복원에서 어느 등식이든 어긋난다 | 복원본을 **쓰지 않는다**. 원본 백업과 절차를 먼저 고친다 | 어긋난 채로 서비스에 붙이기 |

## 6. 금지

- **운영 DB 에 `clean`·`down -v`·`TRUNCATE`·`DROP`.** 리허설의 파괴 명령은 자기가 만든 컨테이너 안에서만 돈다.
  운영 환경에서 이 문서의 어떤 절차도 원본을 파괴하지 않는다 — 복원은 언제나 **새 빈 데이터베이스**로 간다.
- **리허설을 운영 DB 에 겨누기.** `db-rehearsal.sh` 는 원본을 읽기만 하지만, 운영 DB 를 원본으로 주면 백업 산출물이
  운영 데이터를 담은 채 임시 디렉터리에 놓인다.
- **`cleanDisabled` 를 끄는 설정 추가.** 지금 `clean` 이 불가능한 것은 구성의 결과이고, 그것이 방어다.
- **적용된 마이그레이션 파일의 수정.** 체크섬이 바뀌어 다른 환경의 `validate()` 가 깨진다. 되돌림은 §1 의
  forward-fix 로만 한다.
- **백업본을 저장소 안에 두기.**
- **백업 파일에 역할 암호를 담기**(`--no-role-passwords` 를 빼기).

## 7. 알려진 제한

- **논리 백업만이다.** PITR·WAL 아카이브는 이 slice 에 없다 — 운영 반입(M7)의 자리다. RPO 는 백업 주기만큼이다.
- **보존 기간·암호화·저장 위치가 정해지지 않았다.** 리허설의 백업은 실행 안에서만 살고 끝나면 지워진다
  (운영자 결정 A-1 (a)). 고정 저장 자리와 보존 기간은 6B-3·M7 이 정한다.
- **복원 대상 클러스터의 슈퍼유저 이름이 원본과 같아야 소유권이 보존된다.** 다르면 복원 수행 역할로 소유권이
  조용히 옮겨가고 `SECURITY DEFINER` 함수가 누구 권한으로 도는지가 바뀐다. 스크립트는 manifest 가 적은 소유자
  이름으로 대상 클러스터를 만들어 이 축을 닫는다.
- **리허설은 호스트 포트를 열지 않는다.** 복원 대상은 `--network none` 이고, Flyway 호출자는 그 컨테이너의
  네트워크 이름공간을 공유해 루프백으로 붙는다.
- **복원 컨테이너의 임시 암호는 `docker inspect` 에 남는다.** 값은 호스트 argv 를 지나지 않지만, `-e NAME` 으로
  넘긴 값을 데몬이 컨테이너의 `Config.Env` 에 담으므로 docker 소켓에 닿는 사람은 컨테이너 수명 동안 읽을 수
  있다. 매 실행 새로 만드는 난수이고 **아무도 그것으로 인증하지 않으며**(접속은 전부 소켓과 루프백 `trust`)
  포트도 열리지 않는다. 컨테이너와 함께 사라진다.
- **리허설이 검사하는 마이그레이션은 이 checkout 의 것이다.** Flyway 의 classpath 에서 `/jvm/migrations` 가 앱
  이미지의 jar 보다 앞에 선다. 그래서 빌드된 이미지가 checkout 보다 낡으면 체크섬이 어긋나 리허설이 붉어진다 —
  CI 에서는 같은 job 의 앞 step 이 이미지를 먼저 빌드하므로 어긋날 수 없고, 로컬에서 낡은 이미지를 쓸 때 드러난다.
  Flyway·방언·드라이버 자체는 여전히 출하 이미지의 바이트다.
