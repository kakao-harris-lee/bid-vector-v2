## 0. 요약

1. **운영자의 5단계는 옳다. 다만 현실 절차에는 그 사이에 숨은 상태가 넷 더 있다** —
   나라장터 자체 등록(인증서 2종 + 자격 심사 1~5일), 참가신청 마감(일부 공고, 개찰 전날),
   개찰 뒤 「잠정 1위 ≠ 낙찰」의 적격심사 구간(서류 제출 기한 + 심사 7일), 유찰·재공고.
   화면이 이 넷을 모르면 사용자는 매번 나라장터로 되돌아간다(§2).
2. **legacy UI 의 결함은 「단계가 없다」가 아니라 「단계가 있는데 서로 이어지지 않는다」다.**
   투찰서 초안 화면은 사용자 화면 어디서도 링크되지 않는 고아 라우트이고, 실투찰을 기록하는
   화면은 아예 없어 낙찰 결과 자동 확인 체인이 UI 만으로는 시작조차 못 한다. 온보딩은 두 마법사로
   갈라져 같은 필드를 두 곳에 저장한다(§3).
3. **경쟁 서비스는 「맞춤공고 알림 → 관심공고함 → 분석 요청 → 개찰·낙찰 현황」을 표준 골격으로
   쓰고, 투찰 사실 기록은 대체로 서비스 밖(나라장터)에 둔다.** 우리가 차별할 자리는 한 공고를
   **하나의 「입찰 건」 카드가 상태를 갖고 끝까지 흐르는 것**과, 추천가의 근거·기록·복기가 같은
   카드에 남는 것이다(§4).
4. **제약 하나가 설계를 정한다**: 나라장터 OpenAPI 에 「내 투찰 내역」이 없다. 투찰 사실은
   **사용자 입력이 유일한 출처**다(제출확인서 PDF 를 보조 증빙으로). 반면 개찰 결과는 공개
   데이터로 자동 확인된다(1위·참가자수·확정 낙찰자). 따라서 ④는 「입력 부담을 0 에 가깝게」,
   ⑤는 「자동 + 다음 확인 시점 안내」가 설계 원칙이다(§5).
5. **제안 여정은 화면 다섯과 상태 기계 하나**다 — 시작하기(체크리스트) · 오늘의 공고 ·
   공고 워크시트(자격 → 투찰가 → 나라장터 이동 → 기록을 한 화면에서) · 내 입찰함(상태별 +
   타임라인 + 다음 확인 시점) · 결과 확인(§6). 운영자 결정 넷을 §9 에 선택지+추천으로 둔다.

## 2. 현실 절차 — 나라장터에서 실제로 일어나는 일

### 2.1 가입·등록 (①의 바깥)

- **인증서 둘**: 로그인은 **개인용** 공동/금융/간편인증, 최종 전자서명은 **사업자용** 인증서.
  차세대 나라장터(2025-01 개통)에서 지문토큰 의무는 폐지됐다. 인증서 혼동이 첫 번째 페인 포인트로
  꼽힌다.
- **입찰참가자격등록**: 등록분야 선택 → 기본·대표자 정보 → 사업자용 인증서 서명 → 서류
  온라인 제출(PDF 만) → 조달청 심사 **1~5일**. 업종별 추가 서류(건설업등록증 등).
- **소요**: 인증서 1~2일 + 신청 30분~1시간 + 심사 1~5일.

**시사점**: 우리 앱은 이 절차를 대신할 수 없다. 대신 「나라장터 등록 완료 / 인증서 유효기간 /
등록분야」를 온보딩 체크리스트 항목으로 두면, ③에서 「투찰이 안 된다」를 미리 막는다.

### 2.2 공고 확인 (②)

- 공고에는 **입찰 마감일시**와 **개찰일시**가 따로 있고, 일부(PQ·참가신청형)는 **참가신청 마감**
  (관행상 개찰 전날 18:00)이 먼저 온다.
- 낙찰 방식(최저가 / 적격심사 / 협상)과 **복수예비가격 여부**가 투찰 화면과 결과 판독을 바꾼다.
- 자격은 면허·지역·실적·시공능력평가액 네 축(V2 QUAL 축이 이미 소유).

### 2.3 투찰 (③) — 나라장터 화면 실측

가이드 실측 기준 **14개 화면**: 개인 인증 로그인 → 공고 선택·[입찰진행] → 본인확인 →
입찰서류 제출 현황 → **투찰금액 입력** → 금액 확인 + **추첨번호 2개 선택**(복수예가일 때만
팝업) → 법인 인증서 서명 → 완료 → **제출확인서(PDF)**.

반복해서 적히는 실수·주의: 「마감 최소 1시간 전 완료」(과부하) · 「0 을 하나 더/덜」 ·
「하한 미달 즉시 실격」 · 「제출 후 수정 불가, 취소 후 재제출만」 · 「송신실패면 처음부터」 ·
「인증서 만료」. 확인은 「입찰 › 나의 투찰 내역」.

**시사점**: 우리 화면이 줄 수 있는 것은 ⓐ 원 단위 정수 + 한글 금액 병기 + 복사 버튼,
ⓑ 하한 대비 여유 표시, ⓒ 마감 카운트다운(1시간 전 경고), ⓓ 「나라장터 열기」 딥링크다.
자동 제출은 제품 원칙상 하지 않는다(legacy README·roadmap 불변).

### 2.4 개찰 → 낙찰 (⑤) — 상태가 여럿이다

| 상태 | 시점 | 사용자가 아는 것 |
| --- | --- | --- |
| 개찰 완료 | 마감 30분~1시간 뒤(지연 흔함) | 1위·참가자수. **1위 ≠ 낙찰** |
| 적격심사 중 | 1위 통보 뒤 서류 제출(기한은 공고별) → 제출마감일부터 **7일 이내** 심사(+3일 가능) | 부적격이면 차순위로 캐스케이드 |
| 낙찰자 결정 | 공고의 「낙찰자통보 예정일」 | 종합평점 95점 이상 |
| 유찰 / 재공고 | 참가 부족·전원 탈락·계약 포기 | 재공고는 조건이 완화될 수 있음 |
| 계약 | 낙찰 뒤 | 이행보증(통상 10%) 등 — 앱 범위 밖 |

개찰결과 화면은 로그인 없이 낙찰업체·금액·순위·투찰률·탈락 사유를 보여 준다. 우리는 OpenAPI 로
**1위와 참가자수만** 받고 공고번호 표적조회가 안 된다(capability map SET-02 실측). 낙찰 확정은
상호 정규화 매칭으로만 판정한다(SET-01).

> **2026-09-08 — 위 두 문장 가운데 「표적조회가 안 된다」는 폐기됐다(실측).** 운영자 승인 아래
> 실제 조달청 OpenAPI 를 호출해 `inqryDiv=4` + 공고번호 표적조회가 정상 동작함을 확인했다. 또
> 개찰완료 목록 오퍼레이션이 **투찰자별 순위·투찰금액·투찰률**을 필드로 준다(화면과 같은 수준).
> 「1위와 참가자수만」은 기존 구현이 부른 오퍼레이션 집합의 성질이지 API 의 한계가 아니다.
> 정본은 `OPEN-3B2-TARGETED-OPENING-QUERY`(capability map §14.3, 닫힘) — 이 절의 UX 시사점은
> 그 사실 위에서 다시 쓴다.

**시사점**: ⑤는 「낙찰/패찰」 둘이 아니라 위 다섯 상태 + 「아직 수집 전」이며, 각 상태에
**다음 확인 시점**이 붙어야 한다(SET-04 가 요구하던 것). 1순위가 되면 **서류 제출 기한** 리마인더가
낙찰 자체보다 급하다.

## 3. legacy UI 진단 (`bid-vector/frontend/src`, 사용자 번들 `/dashboard`)

### 3.1 화면 재고

하단 탭 넷(오늘 / 입찰 / 투찰 / 결과) + 헤더 아이콘 여덟(온보딩·공고 탐색·업체 정보·전략·가이드·
알림·새로고침·로그아웃). 화면 13개. 라우터 `app/router.tsx`.

### 3.2 5단계에 매핑한 단절

| 단계 | legacy 상태 | 진단 |
| --- | --- | --- |
| ① 가입 이후 | 회원가입 없음(운영자 로그인만). **온보딩 마법사가 둘** — `/dashboard/onboarding`(5단계, 사업자번호+seed 역추천)과 `/dashboard/profile`(4단계, 5축 입력). 홈 CTA 는 후자로만 보내고 전자는 헤더 아이콘으로만 발견. 알림 채널 입력 화면 없음(텔레그램 연동은 admin 전용) | **분할**. 같은 필드(중점 카테고리·지역·금액대·키워드)를 profile 과 strategy 두 곳이 각각 저장 |
| ② 공고 확인 | 후보 목록 `/opportunities`(전략 기반, 칩 5종·정렬 3종, 키워드 검색 없음)와 전체 검색 `/projects`(필터 6종)가 **용어·UI 가 다른 별개 화면**. 카드에 자격 ✅/❌ 없음(강점/리스크 개수만) | **진입점 중복** + STR-16(검색에서 투찰가 요청)의 결합 없음 |
| ③ 투찰가 요청 | 「투찰가 요청」 버튼이 없다. 인라인 `투찰/검토/보류` 는 상태 전환일 뿐. 실제 산출물(투찰서 초안·추천 투찰금액·하한율)은 `/decisions/:id/summary` 에 있는데 **사용자 화면 어디서도 링크하지 않는 고아 라우트**(유일한 링크는 admin `DecisionsScreen`) | **가장 큰 구멍 1** — 핵심 가치가 URL 직접 입력으로만 도달 |
| ④ 투찰 사실 입력 | 백엔드 `POST /operations/real-bids`(금액·하한율·시각·메모)는 있으나 **프론트 호출 0**. `/bids` 탭은 표시만. 빈 상태 문구는 채우는 법을 안 알려줌 | **가장 큰 구멍 2** — 「투찰」 탭이 있는데 투찰을 기록할 수 없다 |
| ⑤ 결과 확인 | `/results` 읽기 전용·자동. 그러나 자동 체인(개찰 1위 → 판정 → 알림)은 **실투찰 등록이 선행 조건**이라 UI 만 쓰면 시작 안 됨. 페이퍼 백테스트 요약이 실제 결과와 같은 화면에 섞임. 「다음 확인 시점」 없음 | ④의 결과로 ⑤가 죽는다. 추정과 실측이 한 화면 |

### 3.3 단계와 무관한 마찰

- **상태 타임라인 부재**: 후보 → 판단 → 투찰 → 개찰 → 낙찰이 탭 넷에 흩어지고, 홈이 같은
  목록 셋을 미리보기로 또 보여 준다.
- **용어 충돌**: 「투찰」이 탭 이름·액션 버튼·금액 세 뜻. 「보류(skip)」가 「나중에」인지 「포기」인지
  불명. 라벨은 정확성을 위해 길다 — 「투찰 기준금액(기초금액/사업금액)」, 「가격 적합도(추정) —
  P(낙찰)이 아닙니다」, 「수행 역량 (0~1)」.
- **모수 없는 점수**: 점수가 없으면 하드코딩 0.64 를 그린다(`Rows.tsx`). 알림 종에 미읽음 배지
  없음, 토스트에 `bid_decision.created` 같은 기계 문자열 노출.
- **빈 상태에 CTA 없음**: 「입찰 후보 없음 / 저장된 입찰 판단이나 최신 페이퍼 후보가 없습니다.」

**결론**: 기능은 대부분 백엔드에 있다. 없는 것은 **한 공고를 끝까지 따라가는 하나의 표면**이다.
legacy `docs/roadmap.md` Phase 4 도 같은 진단을 이미 적었다 — 「오늘 확인할 공고 → 공고 상세/자격
→ 투찰가 요청 → 보고서 → 사용자 결정 → 나라장터 제출 여부 기록 → 개찰 결과 확인까지 끊기지 않는
흐름」과 bid lifecycle 상태 기계(`discovered → … → submitted_external → opened → awarded/lost`).
구현되지 않았을 뿐이다.

리포트)이 여기서 차별점이 된다.

## 5. 설계를 정하는 제약 (사실)

1. **「내 투찰 내역」 API 가 없다.** 조달청 OpenAPI 는 입찰공고·낙찰(개찰결과·1위·복수예가)·
   계약 정보만 공개한다. 투찰 사실은 **사용자 입력이 유일**하다. 보조 증빙은 나라장터 제출확인서
   PDF(사용자가 첨부)뿐이다.
2. **개찰 결과는 표적조회 불가·1위+참가자수만**(SET-02). 전체 순위표는 나라장터 화면에만 있다.
   따라서 「몇 위였나」는 사용자가 나라장터에서 보고 오거나 입력해야 하고, 「낙찰인가 아닌가」는
   상호 매칭으로 자동이다(SET-01, 운영자 요구 「몇 위보다 낙찰 여부」).
3. **자동 제출 금지**(제품 원칙). 나라장터 화면으로 「이동」과 「입력값 복사」까지가 상한이다.
4. **pull 모델**(capability map §0.7): 감시는 제안까지, 투찰가는 요청 시 산출, 강제 작업 큐 없음.
   「내 입찰함」은 사용자가 담은 것만 담는다 — 시스템이 밀어 넣지 않는다.
5. **앱 알림함이 기록이자 회수 경로**(NOTI-10): 채널(텔레그램)은 best-effort, 놓친 것은 알림함에서.

## 6. 제안 여정 — 화면 다섯, 상태 기계 하나

### 6.1 상태 기계 (한 공고 = 하나의 「입찰 건」)

```
후보(제안됨/검색됨)
  → 관심(입찰함에 담음)                      ← 사용자 액션
  → 투찰가 받음(3안 + 근거 + 하한)            ← 요청 시 산출(STR-16·DEC-05)
  → 투찰 예정(초안: 고른 안·시각·공고 스냅샷)   ← 제시 시점에 「이 금액으로 투찰하시겠습니까」로 생성(D-UX-2)
  → 투찰 기록됨(금액·시각·추첨번호·증빙)       ← 사용자 확인 한 번(초안이 기본값, 수정 가능)
  → 개찰 대기(개찰일시까지)
  → 개찰됨: 잠정 1위 / 순위 밖               ← 자동(SET-02)
  → 적격심사 중(1위일 때, 서류 기한 D-n)       ← 사용자 확인 + 공고의 통보 예정일
  → 낙찰 / 패찰 / 유찰·재공고                 ← 자동(SET-01) + 사용자 정정
종료 가지: 건너뜀(사유) · 마감 지남(투찰 미기록)
```

「보류」를 없애고 **「나중에(리마인드 시각)」와 「건너뜀(사유)」**로 나눈다. 모든 전이가 타임라인에
남아 복기의 재료가 된다(roadmap 「투찰 선택 기록 — 감사 가능」).

#### capability 초안 — `BID-01 · 입찰 건의 상태와 전이` (운영자 결정 D-UX-3, 정식 등재 전 초안)

- **사용자 가치**: 사업자가 한 공고를 후보에서 결과까지 **하나의 건**으로 따라가며, 지금 어느 상태이고
  다음에 무엇을 언제 해야 하는지를 한 곳에서 안다.
- **분류(제안)**: `V2 필수` — SET-01·SET-02 의 acceptance 가 「실투찰 등록 공고」를 전제하고, STR-16 의
  요청 경로가 만든 투찰가를 받아 둘 자리가 이것뿐이다. `OPEN-ADR-14` (c) 의 소유 capability.
- **소유**: 위 상태 집합과 전이, 투찰 기록(금액·제출 시각·추첨번호·증빙 참조·메모), 투찰 예정 초안,
  건별 타임라인, 다음 확인 시점. **소유하지 않는 것**: 투찰가 산출(DEC), 자격 판정(QUAL), 개찰 대사
  (SET), 알림 배달(NOTI).
- **Acceptance scenario**
  - 투찰가를 제시받고 안을 고르면 「투찰 예정」 초안이 생기고, 초안에는 고른 금액·제시 시각·그때의
    공고 스냅샷(마감·하한율·basis)이 남는다. 나중에 공고가 정정돼도 초안의 스냅샷은 바뀌지 않는다.
  - 「제출함」 확인은 초안 금액을 기본값으로 하되 다르게 냈으면 수정할 수 있고, 확인 시각과 초안
    시각이 따로 남는다. 확인 없이 마감이 지나면 「마감 지남(미확인)」이 되고 소급 확인이 가능하다.
  - 「투찰 기록됨」 건만 개찰 대사(SET-02) 후보가 되고, 같은 공고에 기록이 여러 번 갱신돼도 건은 하나다.
  - 모든 전이가 시각·주체(사용자/시스템)와 함께 타임라인에 남고, 어느 상태에서도 「다음 확인 시점」이
    비어 있지 않다(없으면 「없음」이 명시된다 — 빈 값 금지).
  - 「건너뜀」은 사유를 갖고, 「나중에」는 리마인드 시각을 갖는다. 「보류」라는 상태는 없다.
  - 페이퍼(가상) 투찰과 실투찰은 같은 상태 어휘를 쓰되 타입이 다르며 같은 목록에 섞이지 않는다.
- **동반 OPEN**: 소급 확인의 허용 기간(개찰 뒤에도 되는가) · 제출확인서 PDF 보관 기간과 저장 위치.

### 6.2 화면

**A. 시작하기 (온보딩 체크리스트, 마법사 하나)**
- 항목: 사업자번호 확인(국세청 상태) → 나라장터 준비(등록 여부·등록분야·인증서 만료일 — 자기
  신고, 미완이면 ③에서 경고) → 자격 5축(면허·지역·실적/시평액·금액대·관심/제외 키워드)을 **한 곳**
  → 알림 채널(앱 기본, 텔레그램·메일 선택) → **첫 공고 미리보기**(후보 없으면 「어느 입력이
  좁혔는지」).
- legacy 의 두 마법사를 하나로 합치고, profile/strategy 가 같은 필드를 두 번 저장하는 구조를
  없앤다. 모든 항목은 나중에 「설정」에서 같은 폼으로 수정.

**B. 오늘의 공고 (홈)**
- 기본 정렬: **마감 임박 × 자격 통과**. 카드 1줄 = 제목 · 발주기관 · 기초금액 · **D-day(참가신청
  마감이 있으면 그것이 먼저)** · 자격 ✅/❌(❌면 무엇이 없어서 — QUAL-01) · 「입찰함에 담기」.
- 같은 화면 상단에 **검색창**(제목·기관·금액대·마감일) — 검색 결과와 제안 목록이 같은 카드·같은
  버튼을 쓴다(STR-16: 검색 결과에서 바로 투찰가 요청). legacy 의 opportunities/projects 이원화를
  없앤다.
- 빈 상태는 이유 + CTA: 「조건에 맞는 공고가 없습니다(아직 수집 전 / 조건이 좁음) → 조건 넓히기」.

**C. 공고 워크시트 (상세 = ②③④를 한 화면에서)**
1. 머리: 제목 · 기관 · 마감/개찰/통보 예정일 · 낙찰방식 · 복수예가 여부 · **카운트다운**.
2. 자격 판정: 축별 ✅/❌ 와 근거 원문(QUAL-05 provenance).
3. **[투찰가 요청]** → 3안(recommended/aggressive/safe) + 근거(기초금액 basis, 하한율·출처,
   유사공고, 과거 오차, 신뢰도) + **판정 불가면 사유**(DEC-04). 입력이 바뀌면 재산출·차이 표시.
   안을 고르면 **「이 금액으로 투찰하시겠습니까?」** 안내가 뜨고, 확인하면 **투찰 기록 초안**이
   만들어진다(고른 안·제시 시각·공고 스냅샷·하한율). 이것이 「내 투찰 내역」의 출발점이다(D-UX-2).
4. **나라장터에서 투찰하기**: 딥링크 + 투찰 입력값 카드(원 단위 정수 · 한글 금액 병기 · 복사 ·
   하한 대비 여유 %) + 체크리스트(인증서 2종, 추첨번호 2개, 제출확인서 저장, 마감 1시간 전).
5. **투찰 기록 확인**(같은 화면, 초안이 채워진 상태): 금액(기본 = 고른 안, 다르게 냈으면 수정) ·
   제출 시각(기본 지금) · 추첨번호 · 제출확인서 첨부(선택) · 메모. **「제출함」 한 번**으로 ④ 완료.
   초안만 있고 확인이 없으면 마감 D-1/D-0 에 「투찰하셨나요?」 알림, 마감이 지나면 「마감 지남(미확인)」
   으로 닫히되 나중에 소급 확인할 수 있다.
6. 타임라인: 이 건의 모든 전이.

**D. 내 입찰함**
- 상태별 탭(또는 칸반): 관심 · 투찰가 받음 · 투찰함 · 개찰 대기 · 심사 중 · 종료.
- 각 카드에 **다음 확인 시점**(마감 · 개찰일시 · 서류 기한 · 통보 예정일)과 지난 일정 경고.
- 페이퍼(가상) 투찰은 별도 탭 또는 별도 화면 — 실측과 섞지 않는다(SET-03 제약).

**E. 결과 확인**
- 건별: 낙찰/패찰/유찰 · 낙찰가 · 내 투찰가 · 차이 · 추천 3안 중 어디였나 · 「역산」(이 금액이면?).
- 1순위가 된 건: **서류 제출 기한 카드**가 결과보다 위.
- 집계: 투찰 대비 낙찰률 · 추천 오차 — 표본 수 병기, 분모 0 이면 「부재」(SET-05 규율).

### 6.3 알림(앱 알림함 = 기록)

트리거 여섯: 새 후보(자격 통과) · 마감 D-1/D-0(투찰 미기록 건) · 개찰 완료(잠정 1위 여부) ·
1순위 서류 기한 D-2 · 낙찰/패찰 확정 · 공고 변경(정정공고). 같은 건은 한 항목이 갱신된다(NOTI-10).
채널은 사용자가 고른 것으로 복제, 실패해도 알림함에 남는다.

### 6.4 용어와 라벨

- 「투찰」은 **나라장터에 낸 행위**에만 쓴다. 탭은 「내 입찰함」, 액션은 「담기 / 투찰가 요청 /
  제출함 / 건너뜀」.
- 라벨은 **2층**: 짧은 라벨(「기초금액」) + 툴팁 정의(「투찰 기준. 추정가격과 다름」). 정직 명세는
  툴팁과 근거 패널로 옮기고 카드 1줄에서는 뺀다.
- 추정치와 실측치는 색·아이콘·위치로 분리, 값이 없으면 빈 자리(가짜 기본값 금지).

### 6.5 최근 UX 관행 — 경쟁 서비스가 안 하는 것 (운영자 지시 2026-09-07: 「타 사이트는 legacy 에
가깝다. 최근 트렌드로 UX 를 제공한다」)

- **다음 행동 하나가 화면을 지배한다**: 카드·상세·입찰함 어디서든 primary 버튼은 그 상태의 다음
  전이 하나(담기 → 투찰가 요청 → 나라장터 열기 → 제출함 → 결과 보기). 보조 액션은 메뉴로.
- **검색 우선·필터는 칩**: 홈 상단 검색창 하나(제목·기관·금액·마감 자연어 입력), 결과 위에 칩으로
  좁힌다. 좌측 필터 패널·페이지 이동 없이 무한 스크롤.
- **점진적 공개**: 카드 1줄 → 펼치면 근거 → 상세는 시트/드로어. 정직 명세·provenance 는 툴팁·
  「왜?」 링크 뒤에.
- **모바일 우선 · 반응형 하나**: 현장에서 폰으로 담고 데스크톱에서 투찰가를 본다. 하단 시트, 큰
  터치 타깃, 원 단위 금액 복사 버튼.
- **상태는 타임라인·D-day 배지로**: 표 대신 건별 세로 타임라인, 다음 확인 시점이 카드 상단 배지.
- **되돌리기 가능한 즉시 반응**: 담기·건너뜀·제출함은 토스트 + 실행 취소, 저장 버튼 없음(자동 저장).
- **빈 상태·로딩·오류의 세 얼굴**: 스켈레톤, 이유 있는 빈 상태 + CTA, 오류에는 재시도.
- **알림함 = 받은편지함**: 읽음/안읽음, 건별 묶음, 클릭하면 그 건의 워크시트로.
- **시스템 색 테마·키보드 접근**: 다크/라이트 자동, 목록 키보드 이동, 포커스 표시.

## 7. 운영자 5단계에 대한 조정 제안

- ①: 「가입」 뒤에 **나라장터 준비 체크**를 넣는다. 앱이 못 해 주는 것을 미리 알린다.
- ②: 「기간 내」는 참가신청 마감을 포함, 「적절한」은 자격 판정 결과를 카드 1줄에.
- ③·④: 요청 → 이동 → 기록을 **같은 화면**에 둔다. 단계를 화면으로 나누면 legacy 처럼 끊긴다.
- ⑤: 「최종」 전에 잠정 1위·심사 중을 보여 주고, 1순위면 서류 기한을 먼저 알린다.

## 8. V2 문서와의 관계 (결정 아님)

- `ADR 0008` D-1~D-4: UI 는 `후속`, 재사용 가부는 M6 6A 계약 뒤. **이 문서는 그 판정에

  없는 것은 **「입찰 건」의 상태와 전이**(`OPEN-ADR-14` 가 지적한 「투찰 계획과 상태」 소유
  capability 부재)와 **투찰 기록(금액·시각·추첨번호·증빙)**이다.
- `OPEN-ADR-09`: 이 문서는 (d) 「UI 마일스톤 신설」의 근거 자료이자, (c) 「legacy 재접속」이
  왜 불충분한지의 근거(§3 — legacy 는 ③④가 끊겨 있어 재접속해도 여정이 안 닫힌다)다.
- pull 모델(§0.7)·NOTI-10·SET-04 의 「다음 확인 시점」 요구와 정합한다.
